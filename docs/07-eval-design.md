# 核心链路评测（设计 + 进度）

> **范围**：只评核心链路 —— **JD 理解 → 经历匹配 → 筛选取舍 → 专用简历成品**。
> 其余 AI 功能（润色、语法、PDF 导入）不做评测，只做「能正常工作」的功能测试。
>
> **与其他文档的关系**：`06-ai-enablement-map.md` 是逐功能的全景图（输入材料），
> 本文是核心链路的**评测实施方案**。`03-generation-algorithm.md` §4.7 / §8 的
> 稳定性验收标准在本文落到具体指标与阈值。

---

## 1. 评的是什么

一次评测跑一个 `(档案, JD)` 组合，产出与人工金标准对比。

```
档案 + JD
   │
   ├─① buildMatchPrompt ──→ 提示词（纯函数）
   │
   ├─② callLLM ──────────→ 模型原始输出
   │
   ├─③ validateMatchResult → MatchAnalysis（判定 / 排序 / 覆盖度）
   │
   └─④ 取舍 + 物化 ──────→ 专用简历成品
```

四步全部 import 生产模块，不复制实现。③④ 之间是 §2.3 的页数取舍。

**评测对象是这条链路的能力，不是单个函数的正确性。** 单个函数的正确性由
`src/lib/match/*.test.ts` 保证（那些测试不调模型）。

## 2. 数据集

### 2.1 一个案例长什么样

```jsonc
{
  "id": "fin-ai-01",
  "note": "金融+AI 档案 × 量化研究员 JD，强匹配场景",
  "dimensions": ["强匹配", "量化充分", "取舍触发"],   // 覆盖维度，见 2.3
  "profileFile": "fin-ai.json",                       // 档案（复用 test-data 的结构）
  "jd": { "company": "云图资本", "position": "量化研究员（机器学习选股方向）", "jdRaw": "…" },
  "gold": {
    "requirements": {                                  // 人工从 JD 拆出的要求项
      "must": ["硕士及以上", "3 年以上量化研究经验", "精通 Python"],
      "nice": ["NLP/大模型金融文本经验", "图神经网络经验", "CFA/FRM"],
      "responsibility": ["因子挖掘与迭代", "组合优化", "研究平台工程化"]
    },
    "entities": {                                      // 逐条人工判定（金标准）
      "<entityId>": {
        "relevance": 3,                                // 0-3 相关度分级，用于排序指标
        "level": "recommended",                        // 二值判定，用于分类指标
        "mustHave": true,                              // 关键经历：不进简历就是失败
        "reason": "直接对应因子挖掘，且有实盘指增产品经验"
      }
    },
    "idealSelection": ["<entityId>", "…"],             // 一页预算下人工认为该放进去的集合
    "targetPages": 1
  }
}
```

**为什么 `level` 与 `idealSelection` 分开**：两者回答不同问题。
`level` 是「这条经历相不相关」，`idealSelection` 是「一页篇幅下到底放哪些」。
一条经历可以很相关但重复冗余，好的简历照样会删掉它。
混成一个标注会导致 AI 无论怎么做都「错」。

### 2.2 标注从哪来

人工标注（我起草 → **你复核**）。AI 生成的标注不能当金标准 —— 那是自证。

**复核方式**：`pnpm eval:review` 生成 `eval-results/review.html`，用浏览器打开。
每个案例摊成「JD + 按相关度排好的经历列表」，**预算线画成列表里一条真实的横线**，
线以上进简历。逐条调相关度，改动会存进浏览器本地，导出成 JSON 交回。
直接看 JSON 复核 118 条判定不现实。

### 2.2.1 标注只有一维

原本 `level`（推荐/不推荐）、`idealSelection`（理想集合）是各写一份的，
于是出现了「集合内有相关度 1、集合外有相关度 2」这种自相矛盾的标注 ——
**AI 判断顺序的唯一信号是相关度，标注自相矛盾时它怎么排都还原不了，
扣的是标注的分，看起来却像模型的错。**

现在两者都由相关度派生，案例文件里只写相关度和「关键经历」：

```
level          = relevance >= 2      （RECOMMEND_THRESHOLD）
idealSelection = 相关度降序取前 budget 条
```

`budget`（一页能放几条）是版面容量，属于估计值，保留为独立字段。
加载时校验预算不得超出相关度 ≥ 2 的条目数，测试里卡住预算线上不得有并列。

### 2.3 覆盖维度（「完备」的判据）

数据集必须把这些维度都铺到，否则指标好看也说明不了问题：

| 维度 | 取值 | 为什么必须覆盖 |
|---|---|---|
| **匹配强度** | 强 / 中 / 弱 / 无关 | 只测二值分类的话，排序质量测不出来 |
| **经历形态** | 量化充分 / 纯罗列无结果 / 一句话短经历 / 跨领域 | 「纯罗列」和「跨领域」是模型最容易判错的两类 |
| **JD 形态** | 硬性明确 / 软性描述 / 隐含要求 / 含干扰项 / 长 JD | 隐含要求漏提取会直接误导用户要不要投 |
| **取舍触发** | 不触发（装得下）/ 触发 / 极端（要砍一半以上） | 决定 §2.3 的三步是否都被走到 |
| **语言噪声** | 中英混排 / JD 含公司介绍废话 | 干扰项排查 |

一个案例可以同时覆盖多个维度（`dimensions` 字段）。

### 2.4 规模

目标 **≥ 15 个案例**，覆盖上面全部维度取值。档案至少 3 份，背景要拉开
（金融+AI / 互联网前端 / 应届或转行 —— 后者经历少，用来测「装得下」路径）。

## 3. 指标体系

分六组。**每组都要有阈值**，否则报告只是数字堆砌。

### A. JD 理解

| 指标 | 定义 | 阈值 |
|---|---|---|
| **缺失项召回** | 人工标注「JD 要求但没有支撑」的技能，被 `coverage.missing` 找出的比例 | ≥ 0.8 |
| **覆盖虚报率** | `coverage.covered` 里人工认为其实没支撑的比例（越低越好） | ≤ 0.1 |

> 缺一条硬性要求会让用户误判要不要投，所以召回优先于准确。

### B. 匹配判定（逐条）

| 指标 | 定义 | 阈值 |
|---|---|---|
| **漏判率（FNR）** | 人工判「推荐」但 AI 判「不推荐」的比例 | ≤ 0.10 |
| **误判率（FPR）** | 人工判「不推荐」但 AI 判「推荐」的比例 | ≤ 0.25 |
| Precision / Recall / F1 | 以 `recommended` 为正类 | 记录，不设阈值 |
| **证据自洽率** | 1 − 自动提升数 / `not_recommended` 数。`autoPromoted` 说明模型引不出否定依据 | ≥ 0.95 |
| **理由幻觉率** | `reason` 里的数字/专有名词在经历原文中找不到的比例 | ≤ 0.05 |

> **漏判比误判严重**：误判用户删掉就行，漏判用户根本不知道自己漏了。
> 所以 FNR 阈值卡得比 FPR 紧一倍以上。

### C. 排序

| 指标 | 定义 | 阈值 |
|---|---|---|
| **NDCG@5** | 人工 0-3 相关度分级 vs AI 的 `rankedIds` 前 5 | ≥ 0.80 |
| **Spearman ρ** | AI 排序 vs 人工相关度排序 | ≥ 0.60 |
| **top-5 命中率** | 人工 top-5 与 AI top-5 的交集 / 5 | ≥ 0.60 |

> 排序服务的是「HR 注意力有限，最匹配的放最前」（§3.7），不是判定对错。

### D. 筛选与成品

| 指标 | 定义 | 阈值 |
|---|---|---|
| **关键经历召回** | `mustHave` 的条目进了简历的比例 | **= 1.00** |
| **理想集合 Jaccard** | 最终简历条目 vs `idealSelection` | ≥ 0.70 |
| **取舍合理性** | 被页数取舍删掉的条目中，人工认为「确实该删」的比例 | ≥ 0.80 |
| **篇幅达成率** | 实际页数 ≤ `targetPages` 的案例比例 | ≥ 0.80 |

> 关键经历召回必须是 1.00：漏掉一条决定性经历，简历就废了。

### E. 稳定性与可复现性

| 指标 | 定义 | 阈值 |
|---|---|---|
| **L1 缓存漂移** | 数据未变重跑，判定翻转的条数 | **= 0** |
| **L2 重跑翻转率** | 同输入跑 N 次，判定不一致的条目比例 | ≤ 0.05 |
| **排序一致性（Kendall τ）** | N 次 `rankedIds` 的两两一致度 | ≥ 0.80 |
| **扰动稳定性** | JD 做语义等价改写（换行/标点/无关措辞）后翻转率 | ≤ 0.10 |

> L1 是设计保证（指纹缓存直接复用，不发请求），必须是 0；
> L2 才是模型本身的抖动。

### F. 成本

输入/输出 token、调用次数、耗时、按模型单价估算的费用。
**不设阈值，但要记录** —— 它决定这个功能能不能默认开启。

## 4. 流程

```
1. 准备数据集（人工标注）           ← 你复核这一步
2. 冒烟：mock provider 跑通全流程    ← 不花钱，验证框架本身
3. 正式跑：真实模型 × N 次
4. 出报告：每指标实际值 vs 阈值 + 通过/不通过
5. 失败案例分析：逐条看漏判/误判的具体内容
6. 归因：是 prompt 的问题、模型的问题，还是标注的问题
```

**第 5 步不能省。** 指标只告诉你「差」，失败案例才告诉你「为什么差、改哪里」。

## 6. 怎么跑

```bash
# 冒烟：不花钱，验证框架本身（oracle 应当全绿）
pnpm eval --transport mock --mock-mode oracle --cache-check --runs 2

# 验证指标真的能抓错（约 1/5 判定被翻面、1/3 排序被打乱）
pnpm eval --transport mock --mock-mode noisy

# 验证稳定性指标（每次调用翻转集合都不同）
pnpm eval --transport mock --mock-mode unstable --runs 3

# 真实跑批
DEEPSEEK_API_KEY=sk-xxx pnpm eval --transport real --provider deepseek --runs 3 --cache-check
```

产物在 `eval-results/<时间戳>/`：`report.md` + `raw/<案例>.json`（含模型原文）。
API key 只从环境变量读，不接受命令行参数 —— 别让它进 shell history。

## 8. 实现中发现的两个坑（已修，记录备查）

**一、`idealSelection` 必须能由相关度还原。**
AI 判断顺序的唯一信号是相关度分级。如果理想集合里有相关度 1 的条目、
集合外却有相关度 2 的，AI 无论怎么排都还原不了 —— 指标扣的是标注的分，
看起来却像模型的错。已加 `lintCases()` 在数据集测试里卡住这条：
入选的最低分必须**高于**落选的最高分（同分跨边界也不行）。

**二、斯皮尔曼在并列时要用平均秩。**
相关度只有 4 档，大量并列。若 gold 侧「并列内部按 id 排」，
这个任意顺序会污染相关系数 —— 全部并列时甚至算出 −1，
看起来像 AI 完全排反了，其实只是 id 顺序不同。
