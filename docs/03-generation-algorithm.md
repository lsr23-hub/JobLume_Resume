## 1. 两种生成模式

| 模式 | 内容选择方式 | 依赖 |
|---|---|---|
| **通用组合** | 确定性规则排序 + 用户手动勾选 | 无 |
| **LLM 智能匹配** | LLM 全量排序 + 逐条理由与命中技能，用户手动勾选 | 需 API Key |
| **手动降级** | 用户完全手动勾选（无 Key 或分析失败时） | 无 |

**三种模式的生成路径完全相同**：简历内容 = 用户勾选的条目。LLM 只影响「界面上多不多一层推荐标注」，不参与生成。后两者共用同一套候选清单 UI，差别仅在有无推荐标注。

## 2. 通用组合（无 JD）

### 2.1 顺序：全选 + 用户自己的排序

无 JD 时**不做排序算法**。全部未隐藏的条目全选，按用户在职业数据库里自己排的顺序（`entity.order`）落位。

**为什么不做自动排序**：早期版本按「时效分 × 同类衰减」自动排序并预勾选（见本节末「设计演进」）。出发点是好的，但产品收缩为「AI 只判定，不动你的文字」（提交 `7168adf`）之后，**勾选状态完全由用户产生** —— 数据库顺序就是用户自己的表达。再叠一层自动排序，等于系统替用户改主意：用户刚在数据库里把某段经历拖到第一，生成简历时又被算法挪走，这是不可接受的。

#### 设计演进：曾经用过、现已移除的排序

早期版本（`rankGeneric`，连同其测试已删除）按下面的规则排序：

```
基础分 = 时效分（3 年内 1.0；3-8 年线性衰减至 0.2；8 年以上 0.2）
最终分 = 基础分 × 0.5^(排在它前面的同类条目数)
```

**它解决的问题是真的**：无 JD 时没有「相关性」可言，而只看「最新」也不够 —— 近期经历若集中在同一领域，纯时效排序会把「什么岗位都能投」的通用简历变成一份领域专用简历。同类衰减（同类的第 2 条 ×0.5、第 3 条 ×0.25，类别取自 `tags[0]`）能让不同领域的经历都进前列。λ=0.5 是唯一的经验参数，语义是「同类经历的第二次出现要新一倍才有同等权重」。

**它被移除不是因为它算错了，而是因为它解决的问题在产品收缩后不存在了** —— 勾选完全由用户产生之后，数据库顺序就是用户的表达，再叠一层自动排序等于替用户改主意。

保留两条仍然成立的结论：

- **顺序不必事先可预测，但必须事后可验证** —— 每条都要能说出它为什么在这个位置。
- **不替用户做他有权自己做的判断** —— 当年刻意不加「同类占比过高时豁免衰减」的兜底，理由是「用户只有金融经历时想投的大概率就是金融岗，压掉同类是错的，但那是用户的判断，不该写进算法」。这条原则恰恰是后来整个算法被移除的原因。

### 2.2 默认勾选建议

**通用组合不设板块上限。** 全部未隐藏的条目**默认勾选**，顺序即 §2.1 的数据库顺序，用户自行增删。

**为什么不再设上限**：v1.0 的 `SELECTION_LIMITS`（经历最多 5 条、项目最多 4 个）是为「AI 自动选择」服务的 —— 系统必须替用户在有限版面内做取舍。改为用户勾选后，这个取舍是用户的事。设一个系统上限只会制造「为什么我的第 6 段经历默认没被选中」的困惑。

**超出页数时**：按 §2.3 处理 —— 提示 + 提供需用户点击的「只保留最近 N 条」。

### 2.3 页数预算

**目标**：一页为最佳，尽量不超过两页。

**三步，从便宜到贵**：

| 步 | 手段 | 改变内容？ | 谁来决定 |
|---|---|---|---|
| 1 | 复用 `useAutoOnePage` 缩放字号与间距（下限 `MIN_SCALE = 0.9`） | 否 | **自动** |
| 2 | 按优先级从尾部移除条目，直到刚好装进目标页数。有 AI 分析时用 AI 序；通用简历退化为数据库顺序（排得最靠后的先删） | **是** | **系统提议，用户点击才生效** |
| 3 | 需砍掉一半以上才装得下 → 改按 2 页给建议 | — | 同上 |

**只有第 1 步是自动的** —— 它不改变内容，只是排版。第 2、3 步必须经过用户确认，
理由与 §3.6「AI 不预设勾选」相同：**删掉经历是不可逆的，系统的建议必须经过用户的动作才生效**。

#### 测量：不导出 PDF

页数由预览现成的分页算法给出（[`src/components/preview/index.tsx`](../src/components/preview/index.tsx)）：

```ts
const pageCount = Math.ceil((contentHeight - 2 * pagePadding) / contentPerPage)
```

`contentHeight` 是**真实 DOM 高度**，代码注释已声明与 Puppeteer PDF 导出一致
（`margin: pagePadding px` 上下各一份）。**不需要真的导出 PDF 就能拿到准确页数。**

第 2 步的试算是**离屏**的：按真实 A4 尺寸渲染候选集合 → 量高度 → 丢弃。
不闪烁；12 条最坏 12 次测量，每次几十毫秒。

**同一份判定必须只有一份实现**：缩放判定（`computeAutoOnePage`）与页数换算
（`pagesOf`）都被生成路径直接引用，而不是各写一遍。

离屏容器走 **portal** 而不是另起 React root：模板内部要用 i18n 语境，
`createRoot` 出来的另一棵树拿不到外层 Provider，模板会整片抛错。

#### 探针必须复刻预览的三个几何条件

离屏测量最容易错的地方不是算法，是**版面上下文**。少任何一个，量出来的高度
和用户在预览里看到的就不是一个数，页数预判直接失效（实测差 8%，正好跨过一页）。
三个条件缺一不可：

| 条件 | 为什么 |
|---|---|
| 版面宽度 = `210mm / scaleFactor` | 预览缩放时把宽度撑到 `1/scale`，视觉换行位置才不变。探针固定按 210mm 排版，换行位置与预览不同 |
| `className="resume-preview"` | 全局样式里有一组 `#resume-preview X, .resume-preview X` 的规则（列表缩进、标题字体）。少这个类名，列表没有缩进也没有上下外边距，整份简历矮一大截 |
| `padding` 与 `fontFamily` 取自 `globalSettings` | 与预览同一份设置 |

第二条是实测踩出来的：探针渲染的是同一个组件、同一个宽度，却比预览矮 220px，
逐段比对才定位到是一组按类名生效的列表样式没命中。

#### 测量成本

一次测量约 400ms（两次 `requestAnimationFrame` + 一整棵模板树的挂载与布局）。
取舍循环每轮一次，14 条最坏 15 次 ≈ 6 秒，全程转圈提示。
按条数二分能省一半，但会改变「删哪几条」的结果 —— §2.3 要求的是从优先级尾部
逐条移除，二分出来的集合不是那个集合。

#### 第 2 步的产物是「提议」

```
⚠️ 当前 2.3 页，超出 1 页
   建议移除这 3 条（AI 认为与岗位最不相关）：
     · 武汉大学 ACM 集训队 —— 与岗位要求无关
     · 日语 —— 岗位未要求日语能力
     · 校学生会技术部 —— 与岗位要求无关
   [ 应用 ]   [ 我自己挑 ]
```

每条都带 AI 给出的 `reason`，用户可以逐条反驳、换一条、或完全自己挑。
点「应用」后进入编辑器，仍可随时把删掉的条目加回来。

**提议出现在新建向导的最后一步**（选完模板之后），而不是编辑器里 ——
生成前定下来，编辑器就不必为此新增任何状态。

按下了「应用」之后，这个「删了哪几条」的决定**不留痕迹**：
不写进 `snapshot`，编辑器里也看不到「这里被 AI 删过」。想要可追溯，
需要另加字段 —— 当前没做，因为 §3.6 的立场是「AI 是推荐者不是决策者」，
把它的建议固化成记录会反过来抬高它的地位。

#### 三种「按什么顺序删」，文案必须分清

| 情况 | 依据 | 界面说明 |
|---|---|---|
| 有匹配结果 | `rankedIds` 倒序 | 「AI 认为与该岗位最不相关的条目」 |
| 有投递目标但未分析 | 数据库排列倒序 | 「该投递目标还没做过 AI 匹配分析……」 |
| 通用简历 | 数据库排列倒序 | 「没有投递目标……」 |

后两种的**排序结果一样，但原因不同**。把它们说成同一句话会让用户以为选错了投递目标。

#### 每个板块至少留一条

裁剪时跳过「该板块只剩一条」的条目。删空会让整个板块从简历上消失 ——
那是结构性改动，该由用户在编辑器里主动决定，不该由「刚好一页」顺手做掉。

代价是可能砍不到目标页数。此时提前结束循环并如实说明（`exhausted`），
剩下的靠精简描述解决。

#### 与 v3 原方案的差异

原方案是「只保留 ★ 优先条目」（固定 top-5）。**固定 5 条与「刚好一页」没有关系** ——
5 条可能仍超页，也可能白白浪费版面。改为**从 AI 优先级序列的尾部逐条移除、
每次重新测量**，直到刚好装进目标页数。

「提议，用户点击才生效」的原则**不变**。

#### 目标页数从哪来

`autoOnePage` 开关即总开关：

| 开关 | 行为 |
|---|---|
| 开 | 生成后自动执行第 1 步；缩不动时给出第 2 步的提议 |
| 关 | 不缩放，只显示当前页数，并提供「帮我精简」入口 |

**生成时默认开启** —— 需求本身就是「一页最佳」，默认拟合是合理的；不想要的在预览面板随手关掉。

> 实现注记：`autoOnePage` 既不在 `DEFAULT_GLOBAL_SETTINGS` 也不在 `initialResumeData` 里，
> 值为 `undefined`（即关闭）。`generateResume` 因此**在生成的 `globalSettings` 里显式写入
> `autoOnePage: true`**，否则第 1 步根本不会发生。

#### 不做描述截断

删掉整段经历用户看得懂，悄悄截断描述会导致句子不完整或语义丢失。

## 3. LLM 智能匹配（有 JD）

> **⚠️ 本节描述的模型契约已过时（v1–v3 时代）。** 下面写的是「模型判定推荐/不推荐 + 逐字举证」；
> **v4 起改为「模型只排序，划线交给代码」**，v5 又把覆盖度改成结构化要求项。
>
> 改动理由与实测数据见 `src/lib/match/buildMatchPrompt.ts` 顶部的版本注释：
> v1 推荐率 79%（人工金标准 43%）、v3 误判率 45.8%。根因不是模型不会判，而是
> **它无从知道该在哪划线** —— 那条线取决于这份简历放得下几条，而这个信息不在 prompt 里。
> 于是划线从模型手里拿走：模型只排序（NDCG 88.8%），截断交给代码，名额由用户在界面上定。
>
> 当前契约：`buildMatchPrompt.ts`（`requirements` / `items[].reason` / `matchedSkills` / `rankedIds`）
> 与 `validateMatchResult.ts`（由名次推导 `level` 与 `inTopN`）。以下章节保留作设计演进记录。

### 3.1 设计原则

| 原则 | 说明 |
|---|---|
| **AI 是推荐者，不是决策者** | LLM 只输出全量名次与逐条理由。**是否放入由用户勾选决定**，AI 不参与生成 |
| ~~二值判断~~ → **模型只排序** | v4 起模型不再输出 `recommended` / `not_recommended`；`level` 由代码按 top-N 推导 —— 划线规则唯一且可复算 |
| **排序用于排版** | LLM 的名次用于目标简历内部的排版顺序与 top-N 归属（`materialize` 的 `priorityOrder`），不是随机展示 |
| **判断解耦** | 每条目对照 JD 独立给出理由与命中技能，不要求模型做条目间的相互论证 |
| **结果可溯源** | 每次分析保存完整结果快照，记录输入指纹与模型信息 |
| **失败必降级** | 任何失败路径都回退为「没有推荐标注的勾选界面」，不出现「功能不可用」 |
| **人工确认是唯一路径** | 简历内容 = 用户勾选的条目。不存在任何自动放入的条目 |

### 3.2 输入构造

发给模型的内容只有三部分：JD、条目清单、输出要求。

**JD 部分**（原文直传，不做预解析）：

```
【目标岗位】
公司：字节跳动
职位：高级前端工程师

【岗位描述原文】
{jdRaw}
```

**条目清单**：每个条目序列化为固定格式。**序列化顺序必须是确定的**（见 §4.2）。

```
{序号}. [{id}] {title} | {subtitle} | {dateRange}
   描述：{description 去 HTML 标签，截断至 300 字}
   技能：{skills 逗号拼接；skills 为空则写「未标注」}
   成果：{metrics 逗号拼接；为空则写「未标注」}
```

**为什么不预解析 JD**：预解析（本地规则或 LLM）会引入一层信息损失。JD 原文里常有「我们希望你…」「团队正在做…」这类上下文，对理解岗位真实需求很重要。直接把原文给模型，让它自己提取。

**为什么 `description` 截断 300 字**：简历的一条经历描述通常在 100-200 字。截断到 300 字足够覆盖全部内容，同时防止个别超长描述挤占上下文。

### 3.3 提示词

```
你是资深招聘顾问，帮求职者判断他的哪些经历最值得放进针对这个岗位的简历。

【目标岗位】
{jdSection}

【候选经历】
{entityList}

【任务】
1. 逐条判断每条经历是否值得放进这份简历，二选一：
   - recommended     推荐：与岗位要求相关，值得放入
   - not_recommended 不推荐：与岗位要求关系不大

2. 在判为 recommended 的条目中，按推荐强度从高到低排序，
   把最值得优先展示的 {topN} 条排在数组最前面。
   （数组顺序即推荐强度，不需要输出名次数字）

【判断规则】
1. 以 JD 原文为准，不要根据职位名称推测要求。
2. 严格按"证据"字段判定：判为 not_recommended 的条目，必须在 "evidence"
   字段中逐字引用该条目描述原文中的一句话作为否定依据。找不到可引用的
   原文，就改判为 recommended —— 无法举证就不该否定。
3. 每条独立判断，不要用"A 比 B 更相关"这类相对表述来定等级。
4. 缺少量化成果不降低推荐与否。只判断与岗位的相关性。
5. 若某条经历与岗位相关但描述写得不好，仍判为 recommended，
   并在 "suggestedFocus" 中说明应该突出什么。
6. 推荐的条目数量不限。宁可多推荐让用户自己删，也不要漏掉相关经历。

【输出格式】
只输出 JSON，不要任何其他文字：
{
  "items": [
    {
      "id": "条目 id，必须与输入一致",
      "level": "recommended | not_recommended",
      "reason": "一句话说明判断依据，40 字以内",
      "evidence": "判为 not_recommended 时逐字引用否定依据；其余填空字符串",
      "matchedSkills": ["从该条目中提取的、与 JD 相关的技能"],
      "missingSkills": ["JD 要求但该条目未体现的技能"]
    }
  ],
  "summary": {
    "recommendedCount": 数字,
    "coverage": {
      "covered": ["JD 要求且数据库中有支撑的技能"],
      "weak": ["JD 要求但支撑薄弱的技能"],
      "missing": ["JD 要求但数据库中没有的技能"]
    },
    "advice": "整体建议，60 字以内"
  }
}
```

**提示词中的每条规则都有具体目的**：

| 规则 | 目的 |
|---|---|
| 任务 2（top-N 排序） | 只影响 top-N 的归属，不影响用户看到的排序。波动被限制在「第 N 与第 N+1 名之间」这一条窄边界上 |
| 规则 2（证据引用） | 用可验证的硬要求替代「请保守一些」这类模糊倾向。模糊标准会让模型每次对「多保守算保守」的理解略有不同，边界条目来回横跳 —— 这是不可复现的主要来源之一 |
| 规则 3（独立判断） | 切断条目之间的依赖。条目 A 的判断不受同批次其他条目影响，批量处理的顺序效应被消除 |
| 规则 4（量化成果不降级） | 防止模型把「描述写得好」误当成「与岗位相关」。这两件事必须分开 |
| 规则 5（弱描述不降级） | 防止模型因为描述写得差就把相关经历判为不推荐。改写是后续环节的事 |
| 规则 6（宁多勿漏） | 推荐漏掉的代价高于多推荐的代价 —— 删是用户主动行为，漏是用户不知道 |

**刻意不写的规则**：不写「请保持结果稳定」「请每次都给相同答案」这类元指令。实测这类指令对稳定性几乎没有作用，反而占用注意力。

### 3.4 输出校验

模型返回后，逐项校验，任一项不通过则丢弃该条并记入日志：

| 校验 | 规则 |
|---|---|
| id 合法性 | `id` 必须存在于本次输入的条目集合中 |
| 无遗漏 | 每条输入条目都应有对应结果；缺失的按 `not_recommended` 处理并在界面标注「未分析」 |
| 无重复 | 同一 `id` 不得出现两次（取第一条） |
| 等级合法性 | `level` 必须是 `recommended` 或 `not_recommended` |
| 顺序完整性 | `rankedIds` 必须包含全部条目的 id，不重不漏 |
| 证据自洽 | `level` 为 `not_recommended` 时，`evidence` 必须非空**且**能在该条目 `description` 的纯文本中找到（子串匹配，忽略空白差异）；否则**提升为 `recommended`** |
| 技能不臆造 | `matchedSkills` 中的每一项必须能在该条目的 `skills` 或 `description` 中找到 |

**证据自洽这条校验是关键**：它把提示词里的软约束变成了程序可验证的硬约束。模型否定一条经历却说不出依据，系统就自动改判为推荐 —— 不依赖模型是否听话。

**注意方向**：举证责任在「否定」一侧。判为推荐不需要举证（宁可多推荐），判为不推荐必须举证。这样既防止模型随手丢弃用户的经历，也让 `evidence` 字段的 token 成本落在一半的条目上。

### 3.5 覆盖度分析

`summary.coverage` 是 LLM 模式下独有的能力，机械打分给不出：

```
✅ 已覆盖 (4)   React、TypeScript、性能优化、工程化
⚠️ 覆盖薄弱 (1) 团队管理 —— 仅在「指导初级工程师」一句提及
❌ 缺失 (2)     WebGL、跨端开发

💡 JD 强调「跨端」，你的 React Native 经历（e8）本次未被选中，
   但可以考虑加入以体现跨端能力。
```

**最后一条是纯 LLM 才能给出的建议** —— 它需要理解「React Native 属于跨端」这个语义关联，标签匹配做不到。

**诚实边界**：`missing` 只报告，不伪造。缺就是缺，工具不帮用户编。

### 3.6 结果呈现

候选清单的 UI 规则：

| 项 | 规则 |
|---|---|
| **默认排序** | 按板块 + 时间倒序。**不按 LLM 的推荐强度顺序** —— 那个顺序只用于计算 top-N 归属（见 §4.1） |
| 标注展示 | 推荐：绿色标记；入选 top-N 的额外加「★ 优先」角标；不推荐：灰色标记 |
| 理由展示 | 每条显示 `reason`；判为不推荐的展开显示 `evidence` |
| **勾选来源** | **勾选状态完全由用户产生**。AI 不预设任何勾选状态 |
| 未推荐条目 | **必须展示**，标注理由。不允许静默隐藏 |
| 手动勾选 | 用户勾选不推荐的条目完全允许，且不显示任何警告 |
| 覆盖标记 | 被用户手动改变状态的条目，标记为「已手动调整」（仅用于「恢复 AI 建议」时识别差异） |

**「勾选状态完全由用户产生」的含义**：没有「默认勾选」这个概念。打开候选清单时所有条目的勾选框都是空的（或统一为未勾选），由用户逐条决定。UI 上提供两个便捷按钮辅助：「全选推荐项」「清空」，但初始状态不由 AI 决定。

**「推荐但未入选 top-N」的语义（已决策）**：

两档判断 + top-N 标记实际产生三档信息，中间那档的含义必须明确：

| 状态 | 界面表现 | 含义 |
|---|---|---|
| `recommended` + `inTopN` | 绿色标记 + `★ 优先` 角标 | 最相关，优先保留 |
| `recommended`（未入选） | 绿色标记 | **同样值得放入**，只是优先级低于带星标的 |
| `not_recommended` | 灰色标记 | 与岗位关系不大 |

**关键**：`inTopN` 只表示**优先级**，不表示**资格**。「未入选 top-N」不是降级，界面文案与配色都不得让它看起来像「次等选项」。

**为什么这样定**：「全选推荐项」会给出一份可能超过一页的简历，用户需要自己删到合适。这比「只推荐 top-N、用户不知道还有别的相关经历」要好 —— **删是用户主动行为，漏是用户不知道**。带星标的条目正好充当「该留哪些」的参考。

**「全选推荐项」的实际效果**：勾选全部 `recommended` 条目（含未入选 top-N 的）。超出页数时按 §2.3 提示用户，不自动删减。

**为什么不做 AI 默认勾选**：一旦 AI 预设了勾选状态，用户会倾向于直接确认而不逐条审视 —— 这就把 AI 从推荐者变回了决策者。留空强制用户过一遍，代价是多几次点击，收益是用户始终清楚「放进简历的是我选的」。

**为什么未推荐的也要展示**：用户需要知道「系统看过我这段经历，判断是不相关」。如果不展示，用户会怀疑「是不是漏了我的经历」，进而不敢信任结果。

### 3.7 AI 排序如何进入简历

**现状缺口**：AI 产出的 `rankedIds`（全部推荐项按推荐强度排序）**没有被生成路径消费**。
`materialize` 的 `pickEntities` 按 `entity.order` 排 —— 也就是用户在数据库里拖拽的顺序。

结果是：AI 花一次调用算出的优先级，在简历上**完全看不到**。

**修正**：`materialize` 接受一个可选的优先级序列。

```ts
pickEntities(profile, sectionId, selection, priorityOrder?)
// 有 priorityOrder → 按它的顺序排
// 没有 → 退回 entity.order（保持现有行为）
```

生成时传入 `matchAnalysis.rankedIds`。序列中没有的条目（例如用户手动勾选的
`not_recommended` 条目）排在后面，内部仍按 `entity.order`。

**效果**：每个板块内，与岗位最相关的经历排在最前 —— 满足「HR 注意力有限，
最匹配的放前面」。

**与 §3.6 不冲突**：§3.6 说的是**候选清单 UI 不按 LLM 顺序排**（避免引导用户的判断），
这里说的是**简历内部的排版顺序**。前者保护用户的选择权，后者服务 HR 的阅读顺序，两回事。

**与 §2.3 是同一套机制**：AI 给出优先级序列 → 排序按它、截断也按它。
一个序列，两个用途。

## 4. 稳定性工程

用户明确要求：**可复现性必须相对较高，不要每次匹配结果相差很远**。本节是实现这个要求的全部手段。

### 4.1 第一道防线：只暴露集合，不暴露排序

**不稳定的来源是排序，不是判断。**

LLM 对单个条目的判断相当稳定 —— 给定同一段经历和同一份 JD，问十次「推不推荐」，答案基本一致。不稳定的是**相对顺序**：两条都被推荐的经历，这次 A 在前、下次 B 在前。

本设计有两处排序，处理方式不同：

| 排序 | 用途 | 是否暴露给用户 | 稳定性处理 |
|---|---|---|---|
| 推荐强度顺序 | 仅用于计算 top-N 归属 | ❌ 不暴露 | 波动只影响「第 N 与第 N+1 名之间」的归属 |
| 条目展示顺序 | UI 列表排列 | ✅ 暴露 | 由「板块 + 时间」这个确定性规则决定，与 LLM 无关 |

**关键点**：用户看到的列表顺序永远不来自 LLM。LLM 的顺序只在一个很窄的地方起作用 —— 决定哪几条能拿到「★ 优先」标记。

**而且 top-N 的误判代价很低**：星标只表示优先级，不表示资格。某条经历这次有星标、下次没有，用户看到的差别只是「一个角标消失了」，它仍然是被推荐的、仍然可以勾选。这与「这次没被选中、下次才被选中」是完全不同的量级。

**量化效果**：假设某条经历的「真实推荐强度」在不同调用间有 ±5% 浮动。在百分制排序下，这会让它在 30 条中的位置浮动 5-10 位（用户直接可见）；在本设计下，只有当它恰好位于 top-N 边界 ±5% 内时，标记才会翻转 —— 而且翻转的是「有没有星标」，不是「排在第几位」。

### 4.2 第二道防线：Prompt 逐字节确定

同一份输入必须产生**完全相同**的 prompt 字符串。任何随机性、时序依赖、对象键序依赖都会让「同一份输入」实际变成「不同份输入」。

| 项 | 规则 | 不做会怎样 |
|---|---|---|
| 条目序列化顺序 | 板块顺序 → `endTimestamp` 降序 → `id` 升序 | 用户拖拽过排序后，prompt 顺序变化，结果跟着变 |
| 缺失 `endTimestamp` | 排在末尾，不调用 `Date.now()` 兜底 | 每次调用时间不同，顺序不同 |
| 不注入历史结果 | 绝不把上次的匹配结果放进 prompt | 结果取决于「跑过几次」，产生路径依赖 |
| 显式排序对象键 | 不使用 `Object.keys()` 的返回顺序 | JS 对象对整数键有特殊排序行为，顺序不可控 |
| 数值格式化 | 固定小数位与单位，不依赖 `toLocaleString` | 不同 locale 环境产生不同字符串 |
| 文本规范化 | `description` 去 HTML 后统一空白符（连续空白压为单个空格）、去首尾空格 | HTML 中的换行与缩进差异会进入 prompt |

**实现要求**：`buildMatchPrompt()` 必须是纯函数，签名形如：

```ts
export function buildMatchPrompt(input: {
  jdRaw: string;
  company: string;
  position: string;
  entities: ProfileEntity[];
}): string;
```

不读全局状态、不调用 `Date.now()`、不依赖 `Math.random()`。给定相同输入，返回值必须逐字节相同（可用单元测试直接断言）。

### 4.3 第三道防线：采样参数

| 参数 | 设置 | 说明 |
|---|---|---|
| `temperature` | `0`（不支持则取最小允许值，如 `0.01`） | 各 Provider 支持情况见下表 |
| `top_p` | 不设置，使用默认 | 同时设 `temperature=0` 与 `top_p` 会相互干扰 |
| `seed` | 支持则设为固定值（如 `42`） | 部分 Provider 支持，能进一步降低波动 |
| 输出约束 | 强制 JSON mode / structured output | 避免自由文本带来的格式波动 |

**v1 锁定 DeepSeek**：本项目 v1 只使用 DeepSeek 一个模型，`temperature = 0`，`seed = 42`（DeepSeek 支持 `seed` 参数，配合 `temperature=0` 能进一步降低波动）。

上游曾内置 4 家 Provider 的配置。本项目**已收缩为 DeepSeek 单通道**（见 [05-api-and-config.md](./05-api-and-config.md) §1）—— 四条通道各自要维护一套请求头、错误格式与前端表单，而实际只用到一条。稳定性验收因此只需针对 DeepSeek 实测。

**注意**：`temperature=0` 不保证严格确定性（浮点运算与批处理顺序仍可能引入差异），但能显著降低波动。这是「相对较高」的可复现性，不是「绝对」。

### 4.4 第四道防线：指纹缓存

前三道防线让结果**倾向稳定**。指纹缓存让结果在数据未变时**完全一致**。

```ts
interface AnalysisCacheKey {
  /** 数据库全部条目的内容字段 + JD 正文 的哈希 */
  contentFingerprint: string;
  /** 模型标识 */
  modelId: string;
  /** 提示词模板版本号，模板改动时递增 */
  promptVersion: string;
}
```

| 情况 | 行为 |
|---|---|
| 指纹一致 | 直接复用上次结果，**零变化** |
| 数据库条目变更 | 提示「3 个条目已修改，建议重新分析」+ 高亮是哪几个（见 §4.5） |
| JD 正文变更 | 提示重新分析 |
| 用户主动点「重新分析」 | 重跑，新旧结果可对比 |
| 模型或提示词版本变更 | 视为缓存失效，提示重新分析 |

**缓存键为什么包含 `promptVersion`**：提示词改动会改变结果。如果不把模板版本纳入缓存键，用户会在「升级了应用」之后拿到一份用旧提示词生成的结果，且无从知晓。

**为什么包含 `modelId`**：换模型必然改变结果。同一个投递目标用 DeepSeek 分析过、又改用豆包，两者结果不可混用。

### 4.5 变更定位

指纹不一致时，不能只说「数据变了」——用户需要知道**是哪条变了**，否则无从判断是否值得重新分析。

```ts
export function diffEntityFingerprints(
  prev: Record<string, string>,   // entityId → 该条目内容的哈希
  next: Record<string, string>
): {
  added: string[];
  modified: string[];
  removed: string[];
};
```

| 变更类型 | 界面提示 |
|---|---|
| 新增 1 条 | 「新增了 1 段经历，建议重新分析以纳入评估」 |
| 修改 2 条 | 「「抖音创作者中台」「组件库建设」有改动，建议重新分析」 |
| 删除 1 条 | 「删除了 1 段经历，当前结果中该条已失效，建议重新分析」 |
| 仅 JD 变更 | 「岗位描述有改动，建议重新分析」 |

**提示而非自动重跑**：自动重跑会让用户在不经意间消耗额度，也会让结果在他没注意时变化。让用户决定。

### 4.6 用户在界面上看到什么

| 位置 | 内容 |
|---|---|
| 候选清单顶部 | 「基于 DeepSeek 分析于 {时间}」+ 「重新分析」按钮 |
| 数据变更时 | 黄色提示条：「{n} 个条目已修改，结果可能不再准确」 |
| 缓存命中时 | 不显示任何提示 —— 结果就是上次的，无需解释 |
| 首次分析 | 「AI 分析结果可能存在细微差异。结果已保存，除非数据变更或你主动重新分析，否则不会改变。」 |

最后一条文案不是免责声明，是**行为说明** —— 它告诉用户「默认情况下结果是冻结的」，这正是他需要的确定性。

### 4.7 稳定性验收标准

| 指标 | 阈值 | 测量方式 |
|---|---|---|
| 缓存命中率 | 数据未变时 100% | 同一投递目标重复打开，结果逐字段相同 |
| **推荐集合稳定性** | 10 次运行，Jaccard ≥ 0.80 | 自动化测试 |
| **top-N 集合稳定性** | 10 次运行，Jaccard ≥ 0.70 | 自动化测试 |
| 推荐数波动 | 10 次运行，推荐条目数的极差 ≤ 3 | 自动化测试 |
| `evidence` 完整率 | 所有 `not_recommended` 条目 100% 有可核对的引用（含被系统提升的） | 自动化测试 |
| prompt 确定性 | 同一输入调用 100 次，输出字符串完全相同 | 单元测试 |

**两个 Jaccard 阈值为什么不同**：

| 集合 | 阈值 | 理由 |
|---|---|---|
| 推荐集合 | ≥ 0.80 | 二值判断，本身就很稳定。若达不到 0.80，说明提示词有歧义，需要修 |
| top-N 集合 | ≥ 0.70 | 依赖推荐强度排序，天然比集合判断多一层波动。放宽是承认这个现实，不是降低要求 |

**Jaccard ≥ 0.80 的含义**：假设稳定有 10 条推荐，10 次运行中每次的推荐集合与「出现次数最多的那一组」相比，平均有 8 条以上重合，最多浮动 2 条。这是「相对较高」的量化定义。

## 5. JD 录入与处理

### 5.1 录入方式

纯手动，不解析（与 [01-PRD.md](./01-PRD.md) FR-JD-01 一致）：

| 字段 | 来源 |
|---|---|
| 公司名称 | 用户填写 |
| 岗位名称 | 用户填写 |
| JD 正文 | 用户粘贴 |
| 备注 | 用户填写 |

**为什么不做自动解析**：JD 解析（无论本地规则还是 LLM）都不改变用户的工作量 —— 用户仍要粘贴正文。多一层解析只是把「填一个好的岗位名」变成「核对 AI 抽取的岗位名」，收益为负。

**JD 原文的价值**：它是后续 LLM 分析的输入。原文保留得越完整，分析质量越高。所以界面上要提示「请粘贴完整 JD，包含任职要求部分」。

### 5.2 JD 质量检查（本地，非 AI）

粘贴后做几项轻量检查，不通过时提示但不阻止：

| 检查 | 提示 |
|---|---|
| 长度 < 100 字 | 「JD 内容偏短，可能影响分析质量」 |
| 不含「要求」「职责」「负责」「优先」等词 | 「这看起来不像完整的岗位描述」 |
| 不含任何数字（年限、人数、百分比） | 「JD 中未发现具体要求，分析结果可能较宽泛」 |

**这些检查是纯字符串匹配**，不调用任何模型。

## 6. 失败与降级

### 6.1 降级矩阵

| 情况 | 行为 | 用户看到 |
|---|---|---|
| 未配置 API Key | 候选清单无推荐标注 | 「未配置 AI，请手动选择要放入简历的经历」 |
| 请求超时 | 重试 1 次（指数退避）。仍失败则无标注 | 「AI 分析超时，请手动选择」 |
| 返回非法 JSON | 重试 1 次并附带格式纠正提示。仍失败则无标注 | 「AI 返回格式异常，请手动选择」 |
| 校验后有效条目 < 50% | 保留已通过校验的部分作为标注 | 「AI 分析结果不完整，请核对后手动选择」 |
| 额度/鉴权错误 | 不重试，无标注 | 「AI 服务不可用（{错误摘要}），请手动选择」 |

**注意降级的本质变了**：在「AI 决定生成内容」的设计里，降级意味着换一条生成路径。在本设计里，**生成路径自始至终是同一条**（用户勾选 → 物化），AI 挂掉只是少了一层推荐标注。降级的实现复杂度因此大幅降低 —— 不需要「手动模式」这个独立状态，只需要 `analysis === null` 时 UI 不渲染标注。

**任何降级路径都产出可用结果。** 不存在「因为 AI 挂了所以生成不了简历」的情况。

### 6.2 无标注状态下的界面

AI 不可用时（未配置 / 失败 / 结果过期），候选清单进入**无标注状态**：

**保留的能力**（与有标注时完全一致）：

- 逐条勾选/取消勾选
- 一键全选 / 清空
- 按板块筛选、按时间排序
- 勾选板块与拖拽排序
- 生成简历

**移除的内容**（仅这些）：

- 推荐 / 不推荐标记
- `★ 优先` 角标
- 理由与依据
- 覆盖度报告

**唯一需要注意的**：无标注状态下不得沿用上次分析的标注。若 `JobTarget.matchAnalysis` 存在但指纹已过期，必须按过期处理 —— 否则用户会误以为那是当前数据下的结论。

**不存在「手动模式」这个独立状态**：生成路径自始至终相同，UI 只是少渲染一个区块。这消除了「模式切换」带来的一整类状态管理问题。

## 7. 可调参数

```ts
// src/config/algorithmConfig.ts

export const MATCH_LEVELS = ["recommended", "not_recommended"] as const;

/** 最推荐条目的数量，用于打「★ 优先」标记 */
export const TOP_N = 5;

export const LLM_PARAMS = {
  /** v1 仅使用 DeepSeek */
  modelType: "deepseek" as const,
  temperature: 0,
  /** DeepSeek 支持 seed，配合 temperature=0 进一步降低波动 */
  seed: 42,
  /** 单条描述进入 prompt 的最大字符数 */
  descriptionMaxChars: 300,
  /** 超过此条目数时启用两阶段粗筛（v1 不实现，预留） */
  twoStageThreshold: 30,
} as const;

export const RECENCY_CURVE = {
  fullScoreYears: 3,
  floorYears: 8,
  floorScore: 0.2,
} as const;

/** 同类经历衰减系数：第二条同类需「新一倍」才能压过别类 */
export const SAME_CATEGORY_DECAY = 0.5;

/** 提示词模板版本，修改 MATCH_PROMPT 时递增 */
export const PROMPT_VERSION = "v1";
```

**`TOP_N` 的取值理由**：一份一页简历通常放 2-4 段经历 + 2-3 个项目，合计 4-7 条。取 `5` 作为「优先展示」的标记数量，与一页简历的容量大致匹配。用户改简历版式时这个值可能不够用，但它是提示不是限制 —— 未打星标的推荐条目同样可选。

**`SAME_CATEGORY_DECAY` 是唯一凭经验设定的参数。** 它不像 v1.0 的 `GENERIC_WEIGHTS` 那样有四个数字假装精确 —— 只有一个标量，语义是「同类经历的第二次出现要新一倍才有同等权重」，凭直觉就能判断合不合适。

## 8. 验证计划

### 8.1 单元测试（纯函数）

| 函数 | 测试重点 |
|---|---|
| `buildMatchPrompt` | **同一输入调用 100 次，输出逐字节相同**；条目顺序符合 §4.2 规则 |
| `parseDateRange`（`lib/profile/entityUtils.ts`） | 「至今」「present」「2021.07」「2021.07-2024.12」等格式；非法格式不抛异常 |
| `validateMatchResult` | 非法 id、重复 id、缺失条目、非法 level、evidence 无法子串匹配时提升为 recommended、`rankedIds` 不重不漏 |
| `diffEntityFingerprints` | 新增、修改、删除的识别 |
| `materialize` | 字段映射正确性、`sourceMap` 完整性、空数据不崩溃 |
| `pageBudget` | 逐条移除后刚好装进目标页数；无 AI 序时退化为数据库顺序；测量失败不挡生成 |

**注意 `extractMetrics` / `extractSkillTags` 已从测试清单移除** —— 这两个函数在 v1 中不再需要（技能与成果的识别交给 LLM）。

### 8.2 稳定性测试（集成，需 API Key）

```
对同一份 (数据库快照, JD) 连续运行 10 次分析（绕过指纹缓存，强制重跑）：
  1. 计算推荐集合的 pairwise Jaccard
  2. 断言平均 Jaccard ≥ 0.80
  3. 计算 top-N 集合的 pairwise Jaccard
  4. 断言平均 Jaccard ≥ 0.70
  5. 计算推荐条目数，断言极差 ≤ 3
  6. 断言所有 not_recommended 条目都有可核对的 evidence
```

**每次运行使用相同的 prompt 与参数**，只让模型自身的非确定性起作用。这样才能测出真实的波动幅度。

**必须绕过缓存**：指纹缓存会让第二次之后的调用直接返回上次结果，测不出任何波动。测试需显式指定「忽略缓存」。

### 8.3 缓存测试

```
1. 分析一次，记录结果 R1
2. 不做任何修改，再次打开 → 断言结果与 R1 逐字段相同（不发请求）
3. 修改一个条目的描述 → 断言提示「1 个条目已修改」
4. 恢复该条目 → 断言指纹回到原值，结果仍复用 R1
5. 修改提示词版本 → 断言提示重新分析
```

### 8.4 降级测试

| 场景 | 断言 |
|---|---|
| 无 API Key | 无标注；候选清单可渲染、可勾选、可生成简历 |
| 断网 | 重试 1 次后无标注，有明确提示；勾选与生成正常 |
| 返回非法 JSON | 重试 1 次后无标注；勾选与生成正常 |
| 返回的 id 全部无效 | 无标注，无崩溃；勾选与生成正常 |
| 额度耗尽（HTTP 429） | 不重试，无标注 + 错误摘要；勾选与生成正常 |
| 分析结果指纹过期 | 不渲染标注（即使 `matchAnalysis` 存在），提示已过期 |

**所有降级场景的共同断言**：候选清单可用、勾选可用、简历能生成。AI 的有无只影响标注是否渲染。

## 9. 与 v1.0 方案的差异

| 项 | v1.0（已废弃） | v3.0（本版） |
|---|---|---|
| 打分主体 | 5 维确定性加权 | LLM 语义判断 |
| AI 的角色 | 微调（±0.15） | 推荐者（不参与生成） |
| 输出形态 | 0-100 分 | 二值推荐 + top-N 标记 + 理由 + 证据 |
| 谁决定简历内容 | 分数决定，用户可覆盖 | **用户勾选，AI 不预设** |
| 排序归属 | 分数决定 | 确定性规则（板块 + 时间）；LLM 顺序仅用于算 top-N |
| `tags` 字段 | 打分主依据 | 保留但系统不填充 |
| `skills` / `metrics` | 打分依据 | 保留但系统不填充，LLM 直读描述 |
| JD 解析 | 本地规则 + AI 结构化 | 不解析，原文直传 |
| 无 Key 时 | 降级为本地打分 | 无推荐标注，生成路径不变 |
| 可复现性手段 | 纯函数天然可复现 | 二值判断 + prompt 确定 + 低温度 + 指纹缓存 |
| 新增代码量 | ~1500 行算法 | ~700 行（prompt + 校验 + 缓存） |

### 9.1 v2.0 → v3.0 的变更（本轮）

| 项 | v2.0 | v3.0 |
|---|---|---|
| 等级档数 | 4 档 | **2 档**（推荐 / 不推荐） |
| top-N | 无 | **新增**，用 `inTopN` 标记 |
| 默认勾选 | 推荐档默认勾选 | **无默认勾选**，勾选状态完全由用户产生 |
| AI 职责 | 给出等级 + 覆盖度 | 同左，但**明确不参与生成** |
| 模型 | 4 家可选 | **v1 锁定 DeepSeek** |
| 举证责任 | `strong` 与 `not_recommended` 都要举证 | **只有 `not_recommended` 需要举证**（无法举证就不该否定） |

**被删除的文件**（v1.0 计划中不再需要）：`skillDictionary.ts`、`synonyms.ts`、`tokenize.ts`、`idf.ts`、`scoreMatch.ts`、`aiAdjust.ts`、`parseJDLocal.ts`、`parseJDWithAI.ts`、`verifyFacts.ts`、`tailor.ts`。

**v3.0 又删除两个**：`extractMetrics.ts`、`extractSkillTags.ts` —— 技能与成果的识别交给 LLM，本地正则抽取不再需要。

**v3.1 按 ponytail 梯子删除五个**：

| 删除项 | 违反的梯级 |
|---|---|
| `provider.ts`（`MatchProvider` 接口） | 一个接口、一个实现、一个调用方 |
| `src/lib/server/aiClient.ts` | 只有一个调用方，为不存在的复用而抽象 |
| `SkillGroup.skillTags` | 死字段：系统不填、算法不读、用户不会填 |
| `ProfileEntity.qualityScore` | 同上 |
| `selectEntities.ts`（约束求解） | 手动勾选后没有「求解」，只剩排序 —— 并入 `rankGeneric.ts` |

**新增的文件**：`buildMatchPrompt.ts`、`validateMatchResult.ts`、`analysisCache.ts`、`fingerprint.ts`、`computeTopN.ts`。

**保留的文件**：`rankGeneric.ts`（时效 × 同类衰减排序）、`materialize.ts`（物化）。

> **后续变更（已落地）**：v3.2 之后模板从 9 套精简到 4 套；改写类 AI 整体移除（提交 `7168adf`）；`rankGeneric.ts` 与其测试随之删除 —— 通用简历改为「全选 + 用户自己的数据库顺序」（见 §2.1）。上面列的 `fingerprint.ts` 职责落在 `analysisCache.ts`，`computeTopN.ts` 没有单独成文件（top-N 由 `buildMatchPrompt.ts` 的 `TOP_N` 常量配合 `validateMatchResult.ts` 计算）。

### 9.2 v3.1 → v3.2 的变更（本轮）

**补的是「AI 结果 → 简历」这一段。** AI 的判定、优先级序列、每条的理由和匹配技能
全都已经算出来了，但生成路径从来没消费过它们 —— 判定结果只在投递目标页展示，
排序序列只用于算 top-N 归属。本轮把它接上。

| 项 | v3.1 | v3.2 |
|---|---|---|
| AI 排序 | 只用于计算 top-N 归属（§3.6） | **同时用于简历内部的排版顺序**（§3.7） |
| 页数超限 | 提示 +「只保留 ★ 优先条目」（固定 top-5） | **按优先级从尾部逐条移除，直到刚好装进目标页数**（§2.3） |
| `autoOnePage` | 上游功能，**默认关闭**（值为 `undefined`） | **生成时默认开启** |
| 篇幅取舍 | 系统不删，只提示超页 | 系统**算出该删哪几条并给出理由**，仍是「提议，用户点击才生效」 |

**没有改动的**（原则一律保留）：

- prompt / 校验 / 缓存 —— **AI 侧零改动**，现有输出够用
- §3.6「候选清单不按 LLM 顺序排」「AI 不预设勾选」—— 保护用户判断
- §2.3「系统的建议必须经过用户的动作才生效」—— 删经历不可逆，不由系统代劳

**新增的代码**（原计划四处，实际落地六处 —— 后两处是实现中发现必须补的）：

| # | 内容 | 落点 |
|---|---|---|
| 1 | `pickEntities` 接受可选优先级序列 | `lib/profile/materialize.ts` |
| 2 | 离屏测量（复刻预览的三个几何条件，见 §2.3） | `lib/profile/measureResume.tsx` |
| 3 | 取舍循环（尾部移除 + 重测） | `lib/profile/pageBudget.ts` |
| 4 | 提议界面（被移除的条目 + AI 理由 + 「应用」／「我自己挑」） | `dashboard/resumes/FitProposal.tsx` |
| 5 | **缩放判定抽成纯函数**，生成路径与预览面板共用 | `hooks/useAutoOnePage.ts` |
| 6 | **「提议」由 `pending` 派生**，不另存一份步骤状态 | `dashboard/resumes/CreateResumeWizard.tsx` |

第 5 条是必须的：预览的页数换算依赖缩放倍率，生成时若各写一份判定，
