## 1. 产品定位

### 1.1 一句话定义

一个本地优先的个人求职工具：把求职者散落在各处的经历沉淀成**结构化的职业数据库**，再针对具体岗位自动筛选、改写、生成针对性简历。

### 1.2 要解决的核心问题

求职时重复劳动集中在三件事上：

1. **重复录入** —— 每投一家公司就要重填一遍教育、经历、项目。信息明明没变，只是排列组合不同。
2. **手工裁剪** —— 同一个岗位 JD 强调「性能优化」，另一个强调「团队协作」，同一段经历要写出不同侧重，全靠人肉判断该突出哪几句。
3. **版本失控** —— 投了 30 家公司后，本地躺着「简历-最终版-v3-字节.docx」这类文件，无法回答「我当时投腾讯用的是哪版、突出的是哪段经历」。

现有工具（超级简历、Canva 简历模板等）解决的是**排版**问题，不解决**内容组织与匹配**问题。

### 1.3 产品原则

| 原则 | 含义 | 反例（明确不做） |
|---|---|---|
| **本地优先** | 所有个人数据存在浏览器本地，不强制联网、不强制注册、不需要服务器账号 | 不做云端账号体系、不做多设备同步（v1） |
| **事实与呈现分离** | 数据库存「事实」，简历存「呈现方式」。同一段经历可以生成十份不同侧重的简历，事实只有一份 | 不允许 AI 编造任何未录入的事实 |
| **智能可降级** | LLM 是加速器不是必需品。不配置 API Key 时，数据库、通用简历、手动组合、版本管理全部可用；仅「智能匹配」退化为手动选择 | 不把 LLM 做成功能的唯一路径 |
| **用户可干预** | AI 的每个判断都必须给出理由与可核对的证据，用户可以覆盖 | 不静默丢弃用户的经历 |
| **结果可复现** | 数据未变时匹配结果零变化；数据变更时提示而非自动重跑 | 不让结果在用户没注意时发生变化 |
| **不覆盖上游** | 二次开发在 `rawproject/` 之外进行，上游代码仅作只读参考 | 不修改 `rawproject/` 下任何文件 |

### 1.4 非目标（v1 明确不做）

- ❌ 求职 CRM（投递状态机、面试跟进时间线）
- ❌ 云端账号与多设备同步
- ❌ 在线简历托管与分享链接
- ❌ JD URL 自动抓取（反爬不稳定，收益低于成本）
- ❌ 海外市场适配（英文简历、ATS 解析、Action Verb 优化）
- ❌ 多人协作

## 2. 用户与场景

### 2.1 目标用户

**主要用户**：正在求职的应届生 / 1-5 年经验社招候选人，投递国内公司，投递量大（10-50 家），岗位方向相近但侧重点不同。

**用户特征**：
- 手头已有一份或几份旧简历（Word / PDF / 招聘网站在线简历）
- 经历条目数量中等（教育 1-3 段、工作/实习 2-5 段、项目 3-8 个）
- 不排斥手动录入，但拒绝重复录入
- 对「AI 会不会瞎编」高度敏感 —— 简历造假在求职中是致命的

### 2.2 核心场景

#### 场景 A：首次建立职业数据库

> 用户手头有一份 PDF 简历，希望一次性导入，之后不再重复录入。

1. 进入「职业数据库」页面
2. 选择导入方式：上传 PDF 简历（复用上游的 AI 解析链路）或手动录入
3. 系统解析出教育、经历、项目等条目，进入**逐条确认**界面
4. 用户确认/修正每条内容。`skills` 与 `metrics` 由 `extract*()` 从描述中自动抽取填充，用户可按需调整
5. 保存，数据库建立完成

**关键体验要求**：解析结果必须逐条确认，不能直接落库。AI 解析简历必然有错漏，未经确认的数据会污染整个数据库。

#### 场景 B：生成通用简历（无明确 JD）

> 用户想先做一份「什么岗位都能投」的基线简历。

1. 进入简历列表，点击「生成通用简历」
2. 系统按「时效 × 同类衰减」排序，全部条目默认勾选（不同类别的经历都能进入前列）
3. 用户增删选中项、切换模板
4. 生成 → 进入编辑工作台微调 → 导出 PDF

#### 场景 C：针对具体 JD 生成目标简历（核心场景）

> 用户看到字节跳动的「高级前端工程师」岗位，想针对性地投。

1. 新建投递目标：粘贴 JD 正文，填写公司名与岗位名
2. 系统做本地质量检查（长度、是否含要求段落）
3. 点击「智能分析」→ LLM 判断每条经历是否值得放，并标出最推荐的 5 条
4. 展示**候选清单**：
   - 每条附推荐标记（推荐 / 不推荐）+ 一句话理由
   - 最推荐的 5 条额外带 `★ 优先` 角标
   - 不推荐的条目展开显示**逐字引用的否定依据**
   - **所有条目的勾选框初始为空** —— AI 不替用户做选择
5. 用户逐条勾选，或用「全选推荐项」快速起步，再手动调整
6. 勾选要展示的板块，拖拽调整顺序
7. 点击生成 → 系统按勾选物化简历 → 进入编辑工作台微调 → 导出
8. 该简历自动关联到此投递目标，可在投递目标详情里找到

**关键体验要求**：

- 第 4 步的候选清单是本产品的核心差异化。用户必须能看懂「AI 为什么这么判断」，否则不敢信。逐字依据是信任的基础 —— 用户可以自己核对。
- **勾选框初始为空是刻意的设计**。AI 给建议，用户做决定。一旦 AI 预设勾选，用户会直接点确认而不逐条审视。

**未配置 API Key 时**：第 3 步跳过，第 4 步的推荐标记不显示，其余流程完全不变。生成路径不依赖 AI。

#### 场景 D：同一 JD 迭代多版

> 用户投完字节后，发现另一家公司的 JD 高度相似，想复用。

1. 复制已有投递目标
2. 修改 JD 正文
3. 系统提示「岗位描述有改动，建议重新分析」
4. 重新分析 → 生成新的简历版本（旧版本保留）

#### 场景 E：投递回顾

> 用户想回顾「我投过哪些公司、用的哪版简历」。

投递目标列表按时间倒序展示，每个目标下挂载其生成的简历版本，可查看当时使用的 JD 与分析结果、导出、删除。

## 3. 功能需求

### 3.1 功能结构总览

```
JobLume Resume
├── 职业数据库（数据层，全量内容存于此）
│   ├── 基本信息（含政治面貌）
│   ├── 教育经历
│   ├── 经历（实习/工作）
│   ├── 项目经验
│   ├── 技能
│   ├── 证书
│   └── 自定义板块（校园经历 / 荣誉课程 / 语言能力 等）
│
├── 简历生成
│   ├── 通用简历（无 JD，规则排序 + 手动调整）
│   └── 目标简历（有 JD，LLM 智能匹配 + 候选确认）
│
├── 简历编辑（复用上游工作台）
│   ├── 板块显示开关与排序
│   ├── 模板 / 字体 / 字号 / 间距 / 主题色
│   └── 内容编辑
│
├── 投递目标管理
│   ├── 新建 / 编辑 / 删除投递目标
│   ├── JD 原文与分析结果查看
│   └── 关联简历版本列表
│
└── 版本管理
    ├── 简历列表 / 复制 / 删除
    ├── 导出（PDF / JSON / Markdown）
    └── 全库备份与恢复（JSON）
```

### 3.2 职业数据库

#### FR-DB-01 板块定义

数据库分**必备板块**与**可选板块**两类。分类只影响「生成简历时的默认展示」，不影响数据库的编辑范围 —— 所有板块在数据库里都可编辑。

| 板块 | 分类 | 数据结构 | 说明 |
|---|---|---|---|
| 基本信息 | 必备（锁定） | `BasicInfo` | 姓名/职位/联系方式/照片/政治面貌等 |
| 教育经历 | 必备（锁定） | `Education[]` | 学校/专业/学位/时间/GPA/描述 |
| 经历 | 必备（锁定） | `Experience[]` | 公司/职位/时间/描述 |
| 技能 | 必备（锁定） | `SkillGroup[]` | 见 FR-DB-03 |
| 证书 | 必备（锁定） | `Certificate[]` | 证书图片或文本条目 |
| 项目经验 | 可选 | `Project[]` | 项目名/角色/时间/描述/链接 |
| 自我评价 | 可选 | 富文本 | 单段文本 |
| 校园经历 | 可选 | `CustomItem[]` | 预设板块 |
| 荣誉课程 | 可选 | `CustomItem[]` | 预设板块 |
| 语言能力 | 可选 | `CustomItem[]` | 预设板块 |

**验收标准**：
- 必备板块在生成简历时默认勾选且不可取消勾选（但可拖拽调整顺序）
- 可选板块默认全部勾选，用户可取消
- 用户可自行新增自定义板块

#### FR-DB-02 条目字段

每个数据库条目包含**内容字段**与**提示字段**两组。

**内容字段**（会出现在简历上）：标题、副标题、时间范围、描述（富文本）。

**提示字段**（不直接出现在简历上，作为 LLM 分析时的补充信号）：

| 字段 | 类型 | 用途 | 是否必填 |
|---|---|---|---|
| `tags` | `string[]` | 粗粒度分类标签，如 `前端` `B端` | 选填 |
| `skills` | `string[]` | 具体技术/能力关键词，如 `React` `Webpack` | 选填 |
| `metrics` | `string[]` | 量化成果，如 `构建时间 8min→2min` | 选填 |

**这些字段在 v2.0 中的角色已改变**：它们不再是本地打分算法的输入（本地方案已废弃），而是给 LLM 的补充提示。全部为空也能正常工作 —— 模型会直接从 `description` 中理解内容。

**验收标准**：
- 提示字段为空时，条目仍可参与匹配，不影响功能可用性
- v1 中系统**不填充**这些字段 —— LLM 分析时直接读 `description` 理解内容。字段保留给用户想显式强调时使用
- **界面不要求用户手动填写** —— 降低录入成本是本设计的主要收益之一

#### FR-DB-03 技能板块的数据结构升级

**背景**：上游项目的技能板块是单个富文本字段（`skillContent`），无法参与匹配。

**需求**：技能拆为「技能组」结构：

```
技能组 {
  名称: string          // 如「前端框架」
  内容: string          // 如「React、Vue.js、Next.js」
  技能标签: string[]    // 用于匹配；留空时自动从「内容」抽取
}
```

**已决策**：技能采用**纯文本列表**形式，不使用熟练度进度条。

| 项 | 决定 |
|---|---|
| 录入形式 | 技能组名称 + 内容文本，如 `前端框架` / `React、Vue.js、Next.js` |
| 展示形式 | 列表项 `前端框架：React、Vue.js、Next.js`（**非进度条**） |
| 匹配依据 | 技能组内容**原样传给 LLM**；LLM 分析时从中提取技能并产出 `matchedSkills` |

**不做本地抽取**：技能名的识别交给 LLM。本地正则抽取需要维护一份技能词典，且无法处理「熟悉 SSR 与同构渲染」这类表述 —— 而 LLM 能直接理解。

**为什么不做进度条**：熟练度是主观自评，用数值做展示会让简历显得浮夸；且 LLM 判断相关度时读的是文字描述，熟练度数值对它没有意义。纯文本列表是国内简历的主流呈现，也最省录入成本。

**约束**：最终渲染仍要落到上游的 `skillContent` 富文本字段，以保证 9 套模板零改动。技能组 → 富文本的渲染在物化层完成，HTML 结构必须与上游 `initialResumeData.ts` 中的示例一致。

#### FR-DB-04 基本信息扩展字段

在 `BasicInfo.customFields`（上游已支持的自定义字段通道）中预设：

| 字段 | 推荐图标 | 默认状态 |
|---|---|---|
| 政治面貌 | `Flag` 或 `UserCheck` | 启用 |
| 个人网站 | `Globe` | 启用（上游已有） |
| 作品集/GitHub | `Github` | 启用 |
| 籍贯 | `MapPin` | 停用（用户可开） |
| 期望薪资 | `Wallet` | 停用 |
| 到岗时间 | `Clock` | 停用 |

#### FR-DB-05 数据导入

支持两种入口：
1. **上传 PDF 简历** —— 复用上游 `/api/resume-import` 的 AI 解析链路
2. **上传 JSON 备份** —— 恢复此前导出的全库备份

**验收标准**：解析结果必须进入逐条确认界面，用户点击「确认导入」后才写入数据库。

### 3.3 通用简历生成

#### FR-GEN-01 排序逻辑

无 JD 输入。按「时效 × 同类衰减」排序，排序结果即默认勾选建议：

```
基础分 = 时效分（3 年内满分，3-8 年衰减至 0.2，8 年以上 0.2）
最终分 = 基础分 × 0.5^(排在它前面的同类条目数)
```

**为什么要同类衰减**：如果近期经历集中在同一领域，纯时效排序会让通用简历变成一份领域专用简历 —— 失去「什么岗位都能投」的意义。衰减确保不同类型的经历都能进入前列。

**类别取自条目的第一个标签**（如「金融」「计算机」「运营」）。未打标签的条目不参与衰减。

**效果**：金融 A、CS、运营 三条不同类经历并列前排；金融 B、金融 C 被依次压下。

**不设板块上限**：全部条目按排序结果默认勾选，用户自行增删。原因见下方验收标准。

**排序结果可验证**：界面上每条显示类别与「同类第 N 条」，用户能看懂为什么它排在那。多样性排序牺牲了「顺序可事先预测」，换来「顺序事后可验证」。

#### FR-GEN-02 生成前预览

生成前展示预览界面：左侧为按排序结果默认勾选的条目列表，右侧为简历渲染预览。用户可拖动排序、取消勾选，确认后落库为一份简历。

**超出页数时**：不自动删减，提示超出并提供「只保留最近 N 条」的一键操作（需用户点击）。

**验收标准**：
- 排序在输入顺序打乱后结果不变（确定性）
- 同一份数据库排序 100 次结果完全一致
- 未打标签的条目不被衰减误伤
- 用户勾选是内容进入简历的唯一途径

### 3.4 目标简历生成

#### FR-JD-01 投递目标录入

| 字段 | 来源 | 必填 |
|---|---|---|
| 公司名称 | 用户填写 | 是 |
| 岗位名称 | 用户填写 | 是 |
| JD 正文 | 用户粘贴 | 是 |
| 备注 | 用户填写 | 否 |

具体录入方式与质量检查见 FR-JD-02。

#### FR-JD-02 JD 录入（不做解析）

**已决策**：JD 不做任何预解析，原文直接作为 LLM 分析的输入。

| 字段 | 来源 | 必填 |
|---|---|---|
| 公司名称 | 用户填写 | 是 |
| 岗位名称 | 用户填写 | 是 |
| JD 正文 | 用户粘贴 | 是 |
| 备注 | 用户填写 | 否 |

**为什么不做解析**：JD 解析（无论本地规则还是 LLM）都不减少用户的工作量 —— 用户仍要粘贴正文。多一层解析只是把「填一个好的岗位名」变成「核对 AI 抽取的岗位名」，收益为负。而 JD 原文中的「团队正在做…」这类上下文对理解岗位真实需求很重要，预解析会引入信息损失。

**本地质量检查**（纯字符串匹配，不调用模型）：粘贴后做几项轻量检查，不通过时提示但不阻止。

| 检查 | 提示 |
|---|---|
| 长度 < 100 字 | 「JD 内容偏短，可能影响分析质量」 |
| 不含「要求」「职责」「负责」「优先」等词 | 「这看起来不像完整的岗位描述」 |
| 不含任何数字（年限、人数、百分比） | 「JD 中未发现具体要求，分析结果可能较宽泛」 |

#### FR-JD-03 LLM 智能匹配

把 JD 原文与数据库全部条目一起发给 LLM，由模型判断每条经历**是否值得放进这份简历**。详见 [03-generation-algorithm.md](./03-generation-algorithm.md) §3。

**AI 的职责边界**：

| 做 | 不做 |
|---|---|
| 判断每条经历推荐 / 不推荐 | 不决定简历内容 |
| 标出最推荐的 N 条（`★ 优先`） | 不预设勾选状态 |
| 给出理由与否定依据 | 不排序展示列表 |
| 输出覆盖度分析 | 不生成或改写简历正文 |

**输出形态**：每条经历一个二值判断 + 一句话理由 + 否定依据（仅不推荐时）。

| 标注 | 含义 | 界面表现 |
|---|---|---|
| `recommended` + `inTopN` | 最相关，优先保留 | 绿色标记 + `★ 优先` 角标 |
| `recommended`（未入选） | **同样值得放入**，优先级低于带星标的 | 绿色标记 |
| `not_recommended` | 与岗位关系不大 | 灰色标记，展开显示否定依据 |

**`★ 优先` 只表示优先级，不表示资格** —— 未入选 top-N 的推荐条目同样是推荐，界面文案与配色都不得让它看起来像「次等选项」。

**不使用 0-100 分，也不用三档以上等级**：档位越少，判断越稳定，用户越容易理解。详见 [03-generation-algorithm.md](./03-generation-algorithm.md) §4.1。

**验收标准**：
- 结果可复现：推荐集合 10 次运行 Jaccard ≥ 0.80，top-N 集合 ≥ 0.70
- **数据未变时不重跑**：指纹一致时直接复用上次结果，结果逐字段相同
- 每个 `not_recommended` 条目必须有可核对的逐字依据

#### FR-JD-04 人工选择与生成

**这是本产品的核心交互，也是唯一的生成路径。**

**已决策**：AI 只做匹配推荐，**简历内容的最终决定权完全在用户手上**。生成步骤不经过 AI。

| 步骤 | 由谁完成 |
|---|---|
| 分析哪些经历与 JD 相关 | AI |
| 标出最推荐的 N 条 | AI |
| **决定把哪些经历放进简历** | **用户（勾选）** |
| **决定展示哪些板块** | **用户（勾选）** |
| **决定板块顺序** | **用户（拖拽）** |
| **生成简历** | **系统按用户的勾选物化** |

**候选清单的交互规则**：

- 每个条目展示：内容摘要、推荐标记、理由；不推荐的展开显示依据
- **未推荐的条目同样展示**，标注理由，不允许静默隐藏
- **勾选状态完全由用户产生，AI 不预设**。打开时所有条目的勾选框均为空
- 提供「全选推荐项」「清空」两个便捷按钮，但初始状态不由 AI 决定
- **「全选推荐项」勾选全部 `recommended` 条目，含未入选 top-N 的** —— 会给出一份可能超过一页的简历，由用户自己删到合适
- 用户勾选不推荐的条目完全允许，不显示警告
- 手动改变过状态的条目标记「已手动调整」
- **列表排序按「板块 + 时间」**，不按 AI 的推荐强度顺序

**勾选超过一页时**：系统**不自动删减**，只提示超出页数，并提供「仅保留 ★ 优先条目」的一键操作（需用户点击才生效）。理由：勾选是用户的决定，系统不替用户删。

**为什么不只推荐 top-N**：那会让用户不知道还有其他相关经历。多推荐、让用户删，优于少推荐、让用户漏 —— **删是用户主动行为，漏是用户不知道**。带星标的条目正好充当「该留哪些」的参考。

**为什么不做 AI 默认勾选**：一旦 AI 预设了勾选状态，用户会倾向于直接确认而不逐条审视 —— 这就把 AI 从推荐者变回了决策者。留空强制用户过一遍，代价是多几次点击，收益是用户始终清楚「放进简历的是我选的」。

**验收标准**：
- 候选清单可用、勾选可用、能生成简历（不依赖 AI 是否可用）
- 用户勾选是内容进入简历的唯一途径
- 未配置 API Key 时，候选清单正常渲染，只是没有推荐标注

#### FR-JD-05 AI 内容改写（v1 不实现）

**v1 不实现**。本版本 LLM 只做分析不做改写。

分析结果中的 `suggestedFocus` 字段（如「把组件复用率与构建耗时优化的数据放在最前」）已经给出改写建议，用户可据此手动调整描述。后续版本再实现自动改写。

**推迟的理由**：改写需要事实校验配套（禁止编造数字、禁止职级僭越），是一套独立的能力，不应与匹配分析捆绑交付。

#### FR-JD-06 覆盖度分析

分析结果中包含整体覆盖度报告：

```
✅ 已覆盖 (4)   React、TypeScript、性能优化、工程化
⚠️ 覆盖薄弱 (1) 团队管理 —— 仅在「指导初级工程师」一句提及
❌ 缺失 (2)     WebGL、跨端开发

💡 JD 强调「跨端」，你的 React Native 经历（e8）本次未被选中，
   但可以考虑加入以体现跨端能力。
```

**最后一条是纯 LLM 才能给出的建议** —— 它需要理解「React Native 属于跨端」这个语义关联，标签匹配做不到。

**诚实边界**：`missing` 只报告，不伪造。缺就是缺，工具不帮用户编造经历。

#### FR-JD-07 简历与投递目标的关联

生成的简历自动记录快照信息：

```ts
{
  mode: 'generic' | 'targeted' | 'manual',
  jobTargetId: string | null,
  jdSnapshot: string,                      // JD 原文快照
  matchAnalysisSnapshot: MatchAnalysis,    // 分析结果快照（含等级、理由、证据）
  selectedEntityIds: Record<string, string[]>,
  manuallyAdjustedIds: string[],
  generatedAt: string
}
```

**分析结果为什么在简历上也存一份**：引用会被后续修改污染。历史简历必须能独立回答「当时依据什么做的决定」，即使投递目标后来被改动或删除。

### 3.5 简历编辑



#### FR-EDIT-01 复用上游能力

上游工作台已提供：三栏布局（板块导航 / 编辑表单 / 实时预览）、板块显示开关与拖拽排序、9 套模板切换、字体/字号/行高/段落间距/板块间距/主题色/页面边距调整、撤销重做、自动一页、语法检查。

**本轮不重做**，仅做以下增量。

#### FR-EDIT-02 增量需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-EDIT-02-1 | 编辑来自数据库的条目时，提示「此内容来自数据库」，并提供「同步回数据库」按钮 | P1 |
| FR-EDIT-02-2 | 展示原版与目标版的段落级差异对照，用户可逐段接受/拒绝 AI 改写 | P1 |
| FR-EDIT-02-3 | 保存当前字体/间距/颜色设置为「我的样式预设」，可复用于新简历 | P2 |
| FR-EDIT-02-4 | 撤销历史持久化（上游为内存态，刷新页面丢失） | P2 |

#### FR-EDIT-03 编辑的默认作用域

**已决策**：在工作台修改一条来自数据库的内容时，**默认只影响当前这份简历**，数据库不变。

| 项 | 行为 |
|---|---|
| 默认 | 改动只写入当前 `ResumeData`，`CareerProfile` 不变 |
| 提示 | 条目顶部显示「此内容来自数据库」，并提供「同步回数据库」按钮 |
| 回写 | 仅当用户点击「同步回数据库」时，才更新 `CareerProfile` 中对应条目 |

**设计理由**：求职中的高频需求是「给这家公司换个说法」，而不是「永久改掉我的档案」。默认回写会让单次微调变得不可能；每次逐项勾选又会让界面复杂化。默认不回写 + 显式同步按钮，语义最清晰：**改简历 ≠ 改档案**。

**UI 提示要求**：来自数据库的条目必须在编辑面板上有明确的来源标识，让用户知道「改这里不会影响我的数据库」。这个提示不能省 —— 否则用户会误以为改动已同步，导致数据库与实际认知不一致。

### 3.6 版本管理

#### FR-VER-01 简历列表

- 展示所有简历，区分「通用简历」与「目标简历」
- 目标简历展示公司名、岗位名、版本号；展开可看当时的分析结果
- 支持按投递目标分组查看
- 支持复制、重命名、删除
- 同一投递目标下的多份简历按生成时间倒序排列，展示为 v1 / v2 / v3

#### FR-VER-01-1 生成策略：每次新建版本

**已决策**：对同一个投递目标重新生成简历时，**新建一份简历**，不覆盖已有版本。

| 项 | 行为 |
|---|---|
| 重新生成 | 创建新的 `ResumeData`，自动命名 `{公司}-{岗位}-v{n}` |
| 旧版本 | 保持不变，仍可在列表中找到 |
| 关联 | 所有版本都挂在同一个 `JobTarget` 下 |

**设计理由**：针对一个岗位重新分析、改选中条目、换措辞是常态操作。覆盖会让「上一版是什么样」永久丢失。简历 JSON 只有几十 KB，存储压力可以忽略 —— 用可忽略的存储成本换取完整的可回溯性，是划算的。

**连带影响**：投递目标详情页需要展示版本列表，而非单个「当前版本」。

#### FR-VER-02 投递目标列表

- 展示所有投递目标，按创建时间倒序
- 每个目标下挂载其生成的简历版本
- 支持编辑 JD、复制目标、删除目标（删除时提示其下的简历如何处理）

#### FR-VER-03 导出

| 格式 | 说明 |
|---|---|
| PDF | 复用上游导出（含长页 PNG / 长页 PDF） |
| JSON | 单份简历导出，可用于分享或在另一台机器导入 |
| Markdown | 复用上游导出，便于粘贴到在线简历平台 |

#### FR-VER-04 全库备份

- **导出**：一份 JSON 包含职业数据库 + 所有简历 + 所有投递目标
- **导入**：支持「覆盖」与「合并」两种模式
- **自动提示**：距上次备份超过 7 天时，在界面提示备份

**验收标准**：导出的 JSON 在另一台机器导入后，数据库、简历、投递目标三者关联关系完整恢复。
