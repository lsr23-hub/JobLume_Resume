## 核心设计一句话

```
职业数据库（唯一事实来源）
      │
      │  无 JD：全选 + 数据库顺序
      │  有 JD：LLM 标注推荐 + top-N  ◀── 仅此一步依赖 AI
      ▼
用户勾选（唯一决策点）
      │  物化 materialize()
      ▼
简历数据 ResumeData（shape 冻结，4 套模板零改动）
      │  渲染
      ▼
PDF / JSON / Markdown
```

**为什么这样分层**：内容会反复重组，排版只有一套。把变化关在数据层，模板层完全冻结，避免改动 4 套模板 × 8 个 section 组件 = 32 个文件。

## 三个产品承诺

1. **事实与呈现分离** —— 数据库存事实，简历存呈现。同一段经历可以生成十份不同侧重的简历，事实只有一份。

2. **AI 是推荐者，不是决策者** —— LLM 只输出优先级排序（每条附理由与命中技能），**勾选状态完全由用户产生**，AI 不预设任何默认值。生成路径自始至终是「用户勾选 → 物化」，与 AI 是否可用无关。

3. **划线不由 AI 决定** —— 模型不做「该不该放进简历」的判断：那条线取决于这份简历放得下几条，而那个信息不在 prompt 里，模型无从知道。它只排序，截断交给代码，名额的最终决定权在用户手里。系统也从不替用户删条目 —— 篇幅不够时只给取舍提案，点了才应用。

## 可复现性设计

用户明确要求「匹配结果不要每次相差很远」。四道防线：

| 防线 | 手段 |
|---|---|
| 一 | **只排序，不判定**：模型不做「推荐 / 不推荐」的二元判断，只给全量名次；`level` 由代码按 top-N 推导，划线规则唯一且可复算 |
| 二 | **prompt 逐字节确定**：固定序列化顺序，禁用 `Date.now()` / `Object.keys()` / `toLocaleString` |
| 三 | **采样参数**：`temperature=0` + `seed=42`，由服务端注入，不接受客户端传值 |
| 四 | **指纹缓存**：数据未变时不重跑，结果**零变化**；变更时提示而非自动重跑 |

验收阈值：推荐集合 10 次运行 Jaccard ≥ 0.80，top-N 集合 ≥ 0.70。

## 通用简历的顺序

通用简历（无 JD）**不做排序算法**：全部未隐藏的条目全选，按用户在职业数据库里自己排的顺序（`entity.order`）落位。

装不下时才谈取舍 —— `planFit` 量一版真实排布的高度，超出页数预算就按同一顺序**从后往前**逐条删（每删一条重新测量，因为条目高度差很大：一条三行的项目经历抵得上四条一行的工作经验），并把删了什么、依据是什么摆给用户看。

**为什么不做自动排序**：早期版本按「时效分 × 同类衰减」自动排序并预勾选，本意是让不同领域的经历都能进前列 —— 因为纯时效会让「什么岗位都能投」的简历退化成领域专用简历。但产品收缩为「AI 只判定，不动你的文字」之后，勾选状态完全由用户产生，数据库顺序就是用户自己的表达；再叠一层自动排序等于替用户改主意。该设计已移除，讨论保留在此作为决策记录。

**顺序不必事先可预测，但必须事后可验证** —— 每条都要能说出它为什么在这个位置（被 AI 排到第几，或因装不下被移除）。
