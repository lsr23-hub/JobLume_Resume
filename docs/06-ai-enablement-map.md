## 一、现状盘点：已经接线但未验证的 AI 面

项目里已有 **4 个 AI 路由**，其中 3 个是上游自带、我没动过的：

| 路由 | 功能 | 来源 | 提供方 | 状态 |
|---|---|---|---|---|
| `/api/match` | JD 匹配经历 | 本项目 | 按 `AIModelType` 走 | **已建，未在界面跑通** |
| `/api/polish` | 经历文本润色 | 上游 | 同上 | 未验证 |

| `/api/resume-import` | PDF 简历识图导入 | 上游 | **仅 Gemini** | 未验证 |

已配置 4 个提供方（`src/config/ai.ts`）：豆包 / DeepSeek / OpenAI 兼容 / Gemini。
`AIModelConfig.validate()` 决定「这个提供方配置完整了没有」—— `match` 与 `polish`/`grammar` 共用这套。

**关键认识**：AI 接入不是从零开始，而是**已有 4 个点，一个都没做质量验证**。总设计要回答的第一个问题不是「加什么」，而是「这 4 个怎么统一评测、哪些值得留」。

## 三、逐点五层链路

### P0 · JD 匹配经历

| 层 | 内容 |
|---|---|
| **功能** | 投递目标页：给定 JD，判定经历池里每条经历的推荐度，标出最推荐的 5 条 |
| **AI 赋能** | 语义匹配（JD 的隐含要求 ↔ 经历的具体内容），这是关键词匹配做不到的部分 |
| **算法设计** | ① **全量单次调用**（不切分、不做向量召回）<br>② **二值输出** + `TOP_N=5` 排序，排序不参与判定<br>③ `temperature=0` + `seed=42` + `PROMPT_VERSION` 版本化<br>④ **证据自洽**：不推荐必须引用原文，引不到自动提升为推荐<br>⑤ **指纹缓存**：内容未变则零调用 |
| **评估指标** | **复现性**（分两层，见下）· **正确性** precision/recall vs 手标注 · **证据自洽率** · **鲁棒性** · 成本 |
| **测试逻辑** | 标注集（多条经历 × 多个方向的 JD）+ N 次重跑 + 语义等价扰动 |

**这一点的评测设计上一轮已详细讨论过，作为其余各点的模板。**

> **复现性必须分两层**（上一轮结论，重申）：
> - **L1 缓存命中**（什么都没改就重新分析）→ 必须 0 漂移
> - **L2 缓存失效**（改了任意一条经历后重跑）→ `fingerprintContent` 是**整体**指纹，改一个字就全量重跑，所以这不是边界情况，是日常路径

### P5 · 经历自动归类与打标

> **类别一半已落地（prompt `t1`）**。词表是**混合的**（行业 + 内容类型）——
> 这不是照原写法来的，是实测逼出来的：`rankGeneric` 的「同类衰减」是**全局**的，
> 而没打标签的条目不参与衰减，所以只给工作/项目按行业打标时，**未打标的条目
> 反而稳稳挤在前面**，top-8 的类别数只有 2、顺序几乎没变。改成混合词表后
> top-8 类别数升到 5，机制才真正按它写的意图工作。
>
> 另一处实测修正：原来的实现「只填空位」，但档案里**早就有手工标签**
> （「计算机」「统计」「数据」），于是这个功能对老用户完全不起作用，而衰减会按
> 各人随手写的字符串分组 —— 写「计算机」的和写「互联网」的其实是同一类却互不衰减。
> 现在是「空位填、非规范值归一化、规范值不动」。
>
> **按既定范围，P5 不进核心链路 eval** —— eval 只覆盖 JD 理解与匹配 / 筛选 / 生成。
> 它的验证是功能测试：19 条单测 + 三个档案共 39 条的真实调用
> （**词表外的值 0 条**，归类逐条人工核对全部正确）+ 浏览器端到端验三条写入规则。

| 层 | 内容 |
|---|---|
| **功能** | 自动填充 `tags[0]`（类别）、`skills`、`metrics` 三个提示字段 |
| **AI 赋能** | 从经历文本抽取结构化标签。这些字段现在**可以全留空**，但 `tags[0]` 兼作类别、直接驱动 `rankGeneric` 的同类衰减 —— 空着通用简历排序就退化 |
| **算法设计** | 拆成两个子任务，**难度与可复现性完全不同**：<br>① **类别**：封闭集分类（金融/互联网/教育/医疗…），可复现性接近 P0<br>② **skills / metrics**：开放集抽取，可复现性差得多<br>—— 建议类别走 LLM 判定，skills 走「**受约束抽取**」（给候选词表，只能从表里选），metrics 走「**只抽不改**」（必须原样摘出原文片段） |
| **评估指标** | 类别：准确率（封闭集，最易测）<br>抽取：precision/recall vs 人工标注<br>**间接指标**：打标后通用简历排序是否更合理 |
| **测试逻辑** | 标注一批 (经历 → 类别/技能/量化点)。**重点测边界**：跨领域经历、只有一句话的短经历、纯罗列的无信息经历 |

### P7 · JD 要求结构化提取

> **已落地（prompt v5）**。走的是下面「算法设计」里那条折中路线的**单次调用**版本：
> 同一次响应里先输出要求项列表（kind / status / entityIds / sourceQuote），再输出经历排序。
> 成本不变。判定由代码硬校验：标 covered 却指不出具体经历就降级为 weak；
> 给出的 JD 原文依据在 JD 里找不到就清空（但**保留这条要求** —— 隐含要求本来就引不出原文）。
> 职责（duty）不参与「缺失」判定。要实测一份：`eval-results/B8-reason说人话/`。
>
> 界面按 kind 分组展示，每条能点到支撑它的经历，并能展开看 JD 原文。
> **没有做要求文本编辑** —— 单次调用下要求列表是叶子节点，改了字没有任何下游影响；
> 且 `r1..rN` 是模型按位置给的、跨运行不稳定，以 id 为键的编辑会在重新分析后静默挂错。
>
> **要求项召回已落地**（`eval/metrics/requirements.ts`，阈值 ≥ 0.90 且在首次测量前定下）：
> 实测 **98.6%**，逐条核对过匹配是真的。已知偏松之处见 docs/07 ——
> 切分粒度差异让约三处部分命中被算作全中。
>
> 下一批：**覆盖判定准确率**（模型给每条要求标的 covered/weak/missing 对不对）。
> 前提是先给金标准补每条要求的状态 —— 那需要逐条对照档案做判断题，
> 而且做的时候极容易被模型输出污染，所以与要求项的原子词粒度一起做。

| 层 | 内容 |
|---|---|
| **功能** | 把 JD 拆成结构化的要求项，逐项对照经历池给出覆盖状态 |
| **AI 赋能** | 现在 `coverage: {covered, weak, missing}` 是**模型一口气给结论**，不可解释、无法验证。结构化后每条覆盖判定都能指向具体经历 |
| **算法设计** | **两条路线，成本差一倍**：<br>① **单次调用**（现状）：便宜，但 coverage 不可验证<br>② **两次调用**：先解析 JD 成要求列表，再逐项判定 —— 可解释、可验证，但误差累积 + 成本翻倍<br>—— 折中：解析出的要求列表**展示给用户可编辑**，把不可验证的中间产物变成可修正的 |
| **评估指标** | **要求项的 recall**（最关键 —— 漏掉一条硬性要求会直接误导用户要不要投）<br>覆盖判定准确率<br>**可解释性**：每条判定能否指向具体经历 |
| **测试逻辑** | 人工列出每个 JD 的「应有要求项」作为金标准，比对提取结果。**重点测**：隐含要求（JD 没明说但显然的）、一条要求拆成多条、软性描述（「有责任心」） |

### P4 · 经历质量诊断

| 层 | 内容 |
|---|---|
| **功能** | 写经历时给改进建议：「这条缺少量化结果」「没说清你的角色」 |
| **AI 赋能** | 评估质量维度并给建议。**只诊断，不改写** |
| **算法设计** | 维度：量化程度 / 角色清晰度 / 动词力度 / 结果可验证性 / 篇幅<br>**每条建议必须引用原文片段**（沿用证据自洽模式）—— 引不到就不该说<br>单条经历独立调用 → 可并行、可缓存、可单独重跑 |
| **评估指标** | **幻觉率必须为 0**（建议里不能出现用户没写过的事实）<br>假阳性率（把已经很好的经历说成有问题）<br>与人工诊断的一致性<br>**终极指标**：建议采纳率（需埋点） |
| **测试逻辑** | 构造两组对抗样本：<br>① 明显有问题的（无量化、无角色、纯罗列）→ 测检出率<br>② 已经很好的 → 测**误报率**。第二组比第一组更重要 |

### P6 · 简历成品诊断

| 层 | 内容 |
|---|---|
| **功能** | 生成简历后整体评估：篇幅、重点、前后一致性 |
| **AI 赋能** | 与 P0 的区别：P0 在**经历池**里选，P6 评估**已生成的成品**（含用户手工编辑过的内容） |

| **测试逻辑** | 准备「有明显问题的简历」（超长、重点错位、与 JD 不匹配）+「干净的简历」，测检出与误报 |

### P8 · 经历结构化改写（风险最高）

| 层 | 内容 |
|---|---|
| **功能** | 把流水账改写成 STAR 结构、补量化 |
| **AI 赋能** | 生成式改写 |
| **算法设计** | **核心风险不是技术问题，是「AI 编数字 = 简历造假」的道德与法律风险**<br>若要做，约束必须远强于其它点：<br>① 输出结构是「**原文片段 → 改写片段**」的映射，不是自由文本<br>② 数字只能来自原文，否则留占位符 `[请填写]`<br>③ 改写结果**逐句可溯源**<br>④ **强制人工 diff 确认**，不提供「一键替换」 |

## 四、跨领域决策（做总设计时**必须先定**的）

这五条比单个功能更重要 —— 它们决定各个点能不能共用一套基础设施。

### 决策 1 · 幻觉边界：三分法

| 类别 | 允许 AI 做什么 | 约束 |
|---|---|---|
| **判定** | 下结论，不改数据 | 证据自洽（引不到原文就不该下这个结论） |
| **建议** | 提意见，用户决定 | 必须引用原文 + 强制人工确认 |
| **改写** | 改文字 | 逐句溯源 + 不引入新事实 + diff 确认 |

**原则**：AI 可以重新组织用户已有的文字，**不可以发明用户没有的事实**。

### 决策 2 · 可复现性策略能否统一

P0 的四道防线（二值判断 / 确定性 prompt / `temperature=0 + seed` / 指纹缓存）里：

- **指纹缓存** → 全部适用
- **二值判断** → 判定类适用；生成类（P8）不适用
- **生成类任务的复现性天然更差** → 阈值要放宽，或改用「结构化输出 + 确定性渲染」（AI 只产出结构化数据，排版交给代码）

### 决策 3 · 证据自洽模式应当推广

P0 的 `validateMatchResult` 是个可复用的手法：**要求模型引用原文，引不到就降级**。这把「不可验证的生成」变成「可验证的生成」。

- P4 的建议必须引用原文片段
- P6 的问题报告必须指到具体段落
- P7 的覆盖判定必须指向具体经历
- P8 的改写必须逐句映射

### 决策 4 · 单次调用 vs 多次调用

现在 P0 是「全量经历一次调用」。若要加 P4/P5/P7，有三种组织方式：

| 方式 | 优点 | 缺点 |
|---|---|---|
| 每功能各调一次 | 简单、失败隔离 | 用户改一条经历要重跑 4 次 |
| 合并成一次「全能调用」 | 便宜 | 输出 schema 复杂、单点失败影响全部、难以单独评测 |
| **分层**（P0 独立；P4+P5 合并成「经历体检」） | 平衡 | 需要设计合并后的 schema |

**已定：P7 走「每功能各调一次」的单次版本**（不是把 P0 与 P7 合并成一次调用，也不是两次调用）。
理由：单次调用里把要求项先输出、排序后输出，可验证性靠代码校验拿到，成本不变。
两次调用真正的收益不在「可验证」（单次也能验），而在**缓存键可以拆成 JD-only** ——
改一条经历不再让要求清单跟着重跑。那条留到需要时再拆，届时 `AnalysisCache` 要多一个槽。

**P4/P5 若要上，仍需重新面对这一条。**

### 决策 5 · 评测基础设施应当共用

所有点都需要同一套评测能力：

```
标注数据管理 · 稳定性(N次重跑) · 正确性(vs 标注) · 证据自洽 · 成本统计
```

**应该建一个通用评测框架，而不是每个功能各搭一套。** 框架必须 import 生产模块（`buildMatchPrompt` 等），不能复制实现 —— 否则测的是个不存在的系统。
