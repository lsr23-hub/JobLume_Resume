# Task Plan: 存档系统改造

> 方案见 `plan/saves-design.md`。本文件只放**执行清单与进度**。

## 工作方式（沿用本项目既有约定）

1. **一次一个阶段**，改完 → 跑检测 → 报告「我的验收结果」+「你的验收流程」
2. **每个阶段结束必须是绿的**：`vitest run` + `tsc --noEmit` + `vite build`（+ 改动涉及的 e2e 套件）
3. 跨文件重构拆成「**纯逻辑先行、再接线**」两步（项目 memory：每个提交都要是绿的）
4. **绝不 glob 删除 `saves/`** —— 那是真实用户数据，清理只能走快照式清扫（项目 memory）
5. 不碰 `saves/` 下已有的真实用户目录

## 已定决策（本轮问过）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 同步模型 | **手动保存为主 + 五个明确写盘时机 + 启动哈希对账**（用户提出，经分析确认可行） |
| 2 | 启动对账 | **哈希比对，只在两边都改时提示**（不静默覆盖任何一边） |
| 3 | 兜底时机 | **加三个上下文切换点**：切用户 / 关编辑器 / 页面隐藏；另外应用内离开用三按钮 |
| 4 | 备份格式 | **全库 zip（含图片二进制）+ 单份 JSON** |
| 5 | 图片 | **二进制落 `saves/<uid>/images/` + 引用**，IndexedDB 降级为缓存 |
| 6 | 部署目标 | **GitHub 开源 + 别人本地部署**；Docker 自托管为主，静态/Workers 降级为纯浏览器模式 |

### ⚠️ 过程中发现并修掉的一个真 bug

`sync()` 原来的守卫是 `if (gaveUp || disabled || !userId) return`。后果：**「已停止自动重试」状态下新做的改动进不了队列** ——
点「保存」时先 `touchProfile()`（触发 sync，被 `gaveUp` 吞掉）再 `flushNow()`（冲一个空队列/旧队列），
界面显示「改动已写入磁盘」而**盘上还是旧内容**。这正是本次要消灭的那类假状态。

修法：只挡 `disabled`，不挡 `gaveUp`。队列长度不会失控（`mergePending` 按 `kind:id` 去重，
上限是一个用户的条目数），而 `schedule()` 仍挡着 `gaveUp`，所以不会自动重试刷屏。

上面「反向验证」的第 4 条就是钉它的 —— 修复前那两条断言会失败。

### 关键设计点

- **哈希由服务端算**（算的是真正落盘的那份），客户端采信返回值。客户端自己只在需要判断「本地是否变了」时算。
- **`stableStringify` 是必需的**，不是洁癖：对象键序取决于插入顺序，而**手改文件**会改变键序（重排、重格式化）——不排序就会让同一条内容算出两个哈希 → 假冲突。
- **逐条隔离、整批不原子**：写多文件做不到跨文件事务，所以不假装能。每条独立成败由 `results` 如实报出。
- **基线的更新放在全部 op 处理完之后**（一次写）：中途更新会把没写成功的条目误记为已同步。
- **基线不带 `[saves]` 前缀**：路由按那个前缀分 400/500，而基线坏了是服务端状态问题。测试专门钉这一条。

   - 旧形状回归 → 单条 `POST` / `DELETE` 响应与改前**逐字节一致**；坏 kind 仍 400
   - 护栏 → 空 `ops`、形状不对的 op、路径穿越 userId 全部 400
3. **往返不变量**（最重要的一条）：用项目自己的 `hash.ts` 从磁盘读回文件重算哈希，
   与服务端回传的、与基线里的三方一致 —— 这一条不成立，客户端就会永远判脏、永远在同步。

### ⚠️ 本轮发现并修掉的一个真 bug（并发写坏基线）

**症状**：真实用户目录里出现了一个 130 字节的 `.baseline.json` —— 前 91 字节是一份完整的
单条基线，其后跟着一段 32 位哈希碎片。`readBaseline` 从此每次都抛错，**那个用户的写盘全挂**。

**根因**：客户端一次 flush 会为**同一个用户**并发发出 N 个请求（旧形状是「每个文件一个请求」，
首屏全量同步时 N 个同时到）。而写入路径是「读基线 → 改 → 写回」的读-改-写：

1. **丢更新** —— N 个请求都读到同一份旧基线，各自写回，只有最后一个的改动留下
2. **文件损坏** —— 两次 `writeFile` 交错：A 截断后写 91 字节，而 B 先前写的更长内容在
   91 字节之后残留

**修法**（两处，缺一不可）：

| 修法 | 解决 | 位置 |
|---|---|---|
| 按用户串行化（`withUserLock`） | 丢更新 | `applySaveOps` 整体加锁 |
| 原子写（唯一临时名 + `rename`） | 半截文件、交错残留 | `writeFileAtomic`，内容文件与基线都走它 |

**反向验证过程中又暴露了第二个隐患**：临时名原本是固定的 `${full}.tmp`，并发时两个写入者
争同一路径 —— 先完成的把文件 rename 走，另一处紧接着 ENOENT。串行化只是**掩盖**了它。
改成每次唯一（`${full}.${randomUUID()}.tmp`）后：

- 去掉锁 → 失败症状变成**正确的那个**（`expected ['resume:r1'] to deeply equal [r0..r7]`，丢更新），ENOENT 不再出现
- 加回锁 → 73/73

**端到端确认**：真实客户端并发 flush（2 文件 → 2 并发请求）后，基线里两条记录都在，
无 `.tmp` 孤儿，内容文件全部合法。

**遗留**：真实用户目录里的坏文件已改名为 `.baseline.json.corrupt` **留档未删**（它是派生数据，
下次写盘会重建正确的 `.baseline.json`）。确认过之后可以删掉它。

端口 3000 的常驻 dev server 当前对 `/api/saves` 返回 404，即**它没带 `SAVES_ENABLED=1`**
（本次会话早先它是好的，进程状态后来变了）。要用界面上的磁盘存档需重启为：
`pnpm dev`（该脚本自带 `SAVES_ENABLED=1`）。我**没有动这个进程**。

### ⚠️ 顺带挖出并修掉一个真 bug：删用户的目录会被写盘追回来

**症状**：删掉用户后 `saves/<uid>/` 过一会儿又出现了。

**根因**：镜像的待写队列里可能还留着这个用户的 op（他在 1.5s 防抖窗口内被删掉），
那批 flush 在目录删掉**之后**落地，`fs.mkdir(recursive)` 把整个目录写回来。

**干净对照实验**（同一 uid，看请求序列）：

| | 请求序列 | 结果 |
|---|---|---|
| 禁用 `discardUser` | `DELETE uid=97cf85c0` → +186ms `POST uid=97cf85c0` | ❌ 目录复活（2/2） |
| 启用 `discardUser` | 只有 `DELETE` | ✅ 目录已删（2/2） |

**修法**：新增 `discardUser(userId)` —— **先等正在飞的那批写盘落地，再丢掉没发出去的队列与基线**，
然后才去删目录。顺序反了等于白删。

### ⚠️⚠️ 排查过程中的一个教训（值得记下来）

**第一次「复现」是假的。** 我用 `page.getByRole("button", { name: "删除用户" }).first()`
点删除按钮 —— 那是**全局**定位，取的是 DOM 里**第一张卡**的删除按钮，与 hover 哪张卡无关。
于是删掉的是**别人**，症状看起来就是「被删用户的目录没消失」，被我误判成竞态。

真正把因果钉死，是在**修好选择器之后**才做到的：修好后禁用/启用 `discardUser` 的对照实验
立刻给出干净的结论（同一 uid 的 `DELETE` → `POST` 追赶）。

**教训**：测试失败时，先确认**测试瞄准的是它以为的那个对象**，再怀疑产品代码。
定位重复控件里的按钮一律**限定在容器内**（`card.getByRole(...)`），不要用全局 `.first()`。
这一条已经写进 `scripts/e2e/saves.ts` 第 5 节的注释里，并留下了常驻断言。

## S3a 记录（已完成）：协议与纯逻辑

按项目纪律拆两步（「纯逻辑先行、再接线」）—— S3a 只做**不改变行为**的部分。

### 为什么 S3 需要先动服务端

客户端要算「哪些改动还没落盘」，就需要**基线**。而基线在磁盘上（S2 放在
`.baseline.json`），客户端读它必须走 `GET /api/saves`。设计文档 §4 也写了
「baseline 随 disk 一起返回」，所以这一步是 S3 的前置，不是 S4 的越界。

**客户端刻意不自己存一份基线** —— 一旦两边各存一份，就会出现「哪份才算数」的问题，
而那正是这套设计要避免的。

### 改动

| 动作 | 文件 |
|---|---|
| 新增 | `lib/saves/baseline.ts`：基线形状 + 键规则（`recordKey` / `parseRecordKey` / `parseBaseline` / `SAVES_SCHEMA_VERSION`）。**前后端共用** —— 与 `kinds.ts` 同一个理由：`lib/server/saves.ts` 引了 `node:fs`，客户端沾不得 |
| 新增 | `lib/saves/session.ts`：`collectDirty`（脏集计算）+ `SavableSnapshot` |
| 扩展 | `lib/server/saves.ts`：`readSaveTree` 现在回传 `baseline`；基线定义改为 re-export 共用模块；错误消息补上补救办法（「删掉它，程序会按内容文件重建」） |
| 扩展 | `lib/saves/tree.ts`：`ParsedUser` 带 `baseline`；注释更新为「已接基线那一半」 |

### 三个设计点

1. **判据是内容哈希，不是引用相等、也不是时间戳**。引用相等只在一次会话内成立
   （刷新后无从比较）；时间戳不可靠（三个 store 的 `updatedAt` 都会被视图操作 bump）。
2. **`collectDirty` 只算「本地 → 磁盘」一个方向**。反方向（要不要把磁盘上的拉回来、

3. **签名放宽为 `SavableSnapshot`**（不要求完整 `CareerProfile`/`ResumeData`）：这个函数
   一个字段都不读，只做哈希。宽松签名把「与数据形状无关」写进了类型里，测试也不必为
   一份完整档案去凑二十个无关字段。

## S3b 记录（已完成大部分）：**去掉自动写盘，改成手动保存为主**

### 改了什么

**模型翻转**：`useSavesMirror` 的 1500ms 防抖自动同步整个退役，换成「编辑只留在浏览器里，
写盘发生在五个明确时机上」。

| 动作 | 文件 |
|---|---|
| 新增 | `hooks/useSavesSession.ts`：把三个 store 与当前用户喂给 session，并把状态推给界面。**这里没有"什么时候写盘"的判断** |
| 新增 | `session.ts` 的会话状态机：`loading`/`ready`/`local-only` + `save()` / `checkUnsaved()` / `canLeave()` / `switchTo()` / `discardUser()` |
| 删除 | `hooks/useSavesMirror.ts`、`hooks/useSavesSyncStatus.ts`、`lib/saves/syncStatus.ts`（+测试）、`lib/saves/mirror.test.ts` |
| 瘦身 | `lib/saves/mirror.ts`：删掉按引用相等的差分、攒批、去重（那些机制随自动写盘一起退役），只留快照与写盘操作的类型 |
| 改造 | `SaveBar` → 「未保存 N 处 · 立即保存」；`SyncStatusBadge` → **全局保存入口**（见下） |

### 三个设计决定

1. **脏集是"算出来的"，不是"记下来的"** —— 从服务端的基线 + 本地内容现算。所以没有队列、
   没有「把失败的放回去」、卸载时丢不掉任何东西。`pagehide` 那一刷失败也无所谓，
   下次打开会重新算出来。
2. **全局徽标扩展成保存入口**。原来它只在失败时出现，而保存栏只挂在职业数据库页 ——
   于是**在简历 / 岗位页改完东西根本点不到保存**，只能靠切用户或离开时兜住。现在徽标
   在有未保存改动时也出现，点它就是保存。
3. **相位 `loading` 与 `local-only` 分开**：前者是"还不知道能不能存"（没有当前用户、
   基线还在路上），后者是"本次部署没有磁盘存档"。两者都**不显示"未保存"** ——
   没有地方可存时，那个数字没有意义。

### ⚠️ 任务计划里那条验收标准是**错的**（已改正）

原文写的是「改一笔不保存 → 刷新 → 仍是「未保存」」。实测发现：**刷新会触发 `pagehide`，
而 `pagehide` 会用 `sendBeacon` 把改动送下去** —— 所以刷新之后是**干净的**，不是"仍未保存"。

那条标准假设了"刷新不会落盘"。正确性性质是**反过来的、而且更好**：关页面时改动不丢。
`e2e:saves` 现在钉的是：

- §4 刷新 → **盘上已经是新内容**（时机 ④ 真的生效）
- §4b 拦掉 POST（模拟卸载时刷不上去：离线 / 服务端挂了 / 载荷超上限）→ 刷新后**仍显示未保存**
  → 证明脏集是从服务端基线重算的，不是内存残留

### `scripts/e2e/saves.ts` 重写（209 → 约 250 行，23 条断言）

现有断言**全部**依赖防抖自动同步（等 2600ms 看文件出现），所以整篇重写。新的八节：

| # | 验什么 |
|---|---|
| 1 | **首屏不写盘** —— 重新打开页面后文件 mtime 不变（旧模型每次开机重写全部文件，缺口 6 由此消失） |
| 2 | 编辑后等 2200ms（比旧防抖还长）→ 磁盘**没被动过** + 界面显示「未保存 N 处」 |
| 3 | 点保存 → 盘上是新内容 + 状态归位 |
| 4 | 刷新 → `pagehide` 兜底把改动送下去了 |
| 4b | 卸载刷不上去 → 下次打开仍认得它没存 |
| 5 | 删条目 → 保存 → 文件消失 |
| 6 | 切用户前自动落盘（时机 ②） |
| 7 | 用户之间互不串目录 |
| 8 | 删用户 → 目录消失且不复现 |

### 与设计文档的两处偏差（都是"设计写的时候模型还没定"）

2. **⑤ 的「不保存」不是"丢弃改动"**。设计写的是「丢弃内存改动（重新从 localStorage 装载
   基线内容）」—— 那句基于旧模型（当时假设基线内容在 localStorage 里、磁盘是真相源）。
   现在反过来：**浏览器是工作副本、磁盘是备份**，"丢弃"没有对象。所以三个按钮是
   「保存并离开 / 直接离开（改动留在浏览器）/ 取消」，文案照这个说。

## S5a 记录（已完成）：图片端点

S5 拆三步：**S5a 只做服务端**，S5b 客户端接线（选中即上传 / IndexedDB 降级为缓存 /
`imageEpoch`），S5c 孤儿 GC。

### 为什么图片要单独一条路

base64 内联会撑爆 localStorage 约 5MB 的配额（设计文档 §6 记着：2-3 张证书就够），
而它同时挡住"备份含图 / 换机器 / 清缓存"三件事。二进制搬出去，数据里只留文件名引用。

### 端点

```
POST   /api/saves/images?userId=&id=   请求体是原始字节，Content-Type 是真实 MIME
GET    /api/saves/images?userId=&name= 回字节 + 正确的 content-type + 长缓存
DELETE /api/saves/images               幂等，供孤儿回收用
```

与 `/api/saves` 同一套 `SAVES_ENABLED` 开关（关掉时 404，同一个契约）与路径校验纪律。

### 两个关键约束

1. **id 与扩展名必须分开校验**。`SAFE_SEGMENT` 刻意不含点（那一条堵死了 `..`），
   所以拿整个 `img_x.jpg` 去过 `isSafeSegment` 会把合法文件名一并拒掉 ——
   按最后一个点切开、两半各校验一次、再拼回去做 `path.relative` 复核。有测试钉住
   （`isSafeSegment("img_x.jpg") === false` 而 `isImageFileName("img_x.jpg") === true`）
2. **扩展名由服务端从 `Content-Type` 推出来，客户端不传**。所以存下来的路径永远由
   服务端拼，客户端左右不了它。白名单只收 jpeg/png/webp/gif/avif（canvas 能编出来的），
   SVG 不在内 —— 它过一遍 canvas 出来就是 PNG

另：客户端传 `id`（`img_<uuid>`）而不是让服务端生成 —— 它要**先把引用写进数据**、
界面才能立刻显示，上传是随后的事。

## S5b 记录（已完成）：三处形态统一，IndexedDB 降级为缓存

### 改之前有三种形态

| 图片 | 以前 | 现在 |
|---|---|---|
| 档案照片 | `idb:img_x`（IndexedDB） | `img_<uuid>.<ext>`（二进制在磁盘） |
| 简历照片 | 内联 data URL | 同上 |
| 证书 | 内联 base64（还带一套三档压缩） | 同上 |

后两种会撑 localStorage 约 5MB 的配额，而且让「备份含图 / 换机器 / 清缓存」三件事同时失效。

### 三个关键决定

1. **强制 `img_` 前缀**。少了这条，任意一个长得像文件名的字符串都会被当成引用去查 ——
   而照片字段里确实可能写着 `/avatar.png` 这样的静态路径。加上前缀之后，"是不是引用"
   这个问题才有确定的答案（`isImageRef('/avatar.png') === false` 有测试钉住）
2. **选中即上传**（不等手动保存）。图片是素材不是文档，没有"草稿"语义；延后上传会造出
   "数据已保存但照片没保存"这种没法向用户解释的中间态。顺序是**先写缓存再上传** ——
   缓存写完界面就能显示
3. **`imageEpoch`**：字节是**后到**的（缓存没有时从磁盘拉），而渲染侧 effect 的 deps
   只看"引用变了没有" —— 引用没变、deps 不动，界面就一直空着。加一个计数器，
   从磁盘取到图就 +1，三处 effect（`useResolvedImage` / `preview` / `BasicPanel`）把它放进 deps

`deleteImage` / `countImageRefs`（全仓零引用）、`getImageBlob` 收回私有。

## S5c 记录（已完成）：孤儿图片回收 —— **缺口 2 闭合**

### 时机与范围

**保存成功之后**跑（由路由调用），不做定时任务 —— 只在明确的时刻跑，行为可预测。
不回收的话，换过照片、删过证书的旧文件会永远留在盘上越攒越多。

扫描范围定得死：图片只可能出现在三处 —— **档案照片 / 简历照片 / 证书 url**。
富文本里插不了图（tiptap 的依赖里没有 `extension-image`），所以正文不用扫。

### 两条安全阀，缺一不可

1. **刚写进来的不动**（`ORPHAN_IMAGE_GRACE_MS = 1 小时`）。图片是"选中即上传"的：
   字节先落盘、引用要等用户保存数据才写进 `*.json`。这中间它在磁盘的数据看来就是孤儿，
   而它其实是用户刚选的
2. **数据读不出来就放弃这次回收**。一份坏掉的 `resume.json` 会让它引用的图片全变成
   "孤儿"被删掉 —— 所以 `collectReferencedImages` 读不出来时**抛错**，路由那边是
   best effort，下次保存再来一次

另：路由只在**全部 op 都成功**时才回收 —— 有失败的话磁盘上的数据不是最新的，
拿它当"引用了哪些图"的依据会把失败那条的图误判成孤儿。

### ⚠️ 单测抓到的一个真 bug

宽限期原本写的是 `now - stat.mtimeMs < graceMs`。**文件的 mtime 可能比 `now` 晚一毫秒**
（时间戳粒度），差值成了负数，于是 `graceMs = 0` 时反而把刚写的保护了起来。
改成显式比较时间点：`graceMs > 0 && stat.mtimeMs >= now - graceMs`。

它是**偶发**的 —— 单独跑那个文件时通过，跑全量时失败（时钟竞态）。修法同时消除了 flakiness。

**bind mount 而不是命名卷。** 这个应用的心智模型是「文件夹就是我的数据」——
用户要能直接在宿主机上看到 `saves/`、拷走它、放进自己的备份。命名卷把那件事藏起来了。
代价要写清楚：容器以 uid 1001 运行，所以宿主机那个目录要让它写得进去
（README 给了 `chmod 777 saves` 或改 Dockerfile uid 两条路）。

**端口默认绑回环。** 数据（姓名、联系方式、完整经历）就在那个目录里，不该一上来就对
局域网敞开。没想过这件事的部署会**失败关闭**。

**限流的额度必须宽松**（300/分）。它承载正常使用 —— 导入一个带几十张图的备份就会连着
发几十个请求。这里挡的是脚本刷盘，不是人。
**实测证明它真的生效**：320 个并发请求 → 300×200 + 20×429（与配置精确一致）。

**CI 不跑 e2e。** 那 9 套要 dev server + 真实 Chromium，单次几分钟，而且它们要抓的问题
（真实渲染、PDF 文字层、图片解码）在 CI 里更容易因环境差异变成假红。它们是
「改完主链路后手工跑一遍」的验收工具（`scripts/e2e/README.md` 写着）。

**不做自己的账号体系。** `/api/saves` 匿名可调用，谁访问到站点谁就能读写全部数据。
README 给的是反向代理 basic-auth 的现成做法（Caddy 示例）—— **发明一套鉴权比用代理层
风险大得多**。

### README 改了什么

- **部署**：三种方式（Docker / node / 本地 dev）+ 环境变量表（只讲三个要紧的）+ `TRUST_PROXY` 的坑
- **新增「⚠️ 对外开放之前必须做的两件事」**：加一层认证（含 Caddyfile 示例）、想清楚

- **项目结构**：补上 `lib/saves/` 的分层表与 `routes/api/`

### D36 记下的东西

**三条否决理由**（为什么不选另外三条路）：

1. **时间戳不可靠** —— 三个 store 的 `updatedAt` 都会被**视图操作** bump（切板块标签、
   拖项目顺序都会让简历「变新」），按它判断谁更新会静默覆盖真实编辑；内容哈希只回答
   「这条比上次同步时变了没有」，不依赖时钟也不需要合并算法
2. **浏览器不留数据会让没有服务端的部署彻底不可用**（Workers 没有 `node:fs`、静态托管
   连端点都没有），而保留 localStorage 时读盘失败只降级成「纯浏览器模式」
3. **单向镜像挡住产品要的心智模型** —— 清缓存不丢、手改文件生效、换机器可用，单向一件都做不到

**三条已知边界**：冲突逐条问（刻意不自动合并）；「本地没有 + 磁盘有」选恢复；
多标签页后写覆盖先写（未处理）。另：**D35 那条「删用户不删目录」的边界随之消失**。

### ⚠️ 真的冲突：Source Han Serif 的保留字体名

OFL 规定**修改版不得使用保留字体名**，而**子集化就是修改版**。Source Han Serif 的 OFL
声明了 `Reserved Font Name 'Source'`，而我们的子集文件名（`SourceHanSerifSC-*`）与字体
**内部名**（`Source Han Serif CN`）都踩中了。

修法（用户选「改名，保留这个字族」）：内部名 → `Han Serif CN`、文件名 → `HanSerifSC-*`、
**版权声明原样保留并追加说明**（那是 OFL 要求随附的 notice，也正是 RFN 声明的来源）、
新增 `scripts/rename-subset-font.py` 并接进 `pnpm subset:fonts`。

另补齐：两份 OFL 许可证文件、`public/fonts/README.md` 的「许可证」一节（含 **MiSans 的
署名义务** —— 官方 FAQ 明写「您应在软件中特别注明使用了 MiSans 字体」）。

一处我自己的更正：中途报过 Noto 也带 RFN，复查发现是把 **OFL 正文里的条款**当成了声明
（`noto-cjk` 的 LICENSE 没有 RFN 行），Noto 一直合规。
